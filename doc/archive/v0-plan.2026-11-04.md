# RSI-native 推理引擎 v0 计划

- 日期：2026-11-04
- 状态：已和发起人逐项讨论确定的计划稿。第 1 节是讨论中确定的决策，其余是据此展开的设计。凡是本文自行补充、尚未讨论确认的地方，都标注了"（待确认）"。
- 关联文档：[discussion-summary.md](discussion-summary.md)（背景、调研、原始架构决策 D1–D14）。本文和它冲突时，以本文为准。
- 修订记录（均为 2026-11-04）：
  1. v0 不做鉴权和角色，也不区分线上和开发。
  2. **撤回模拟器方案。** 原计划用"语义哈希执行器 + 代价模型"代替真实执行，现在改为 v0 直接接真实后端。撤回的理由：写这样一个模拟器的工作量可能比接真实后端还大，而且它是一套和真实实现分叉的第二实现，最终会失去意义。
  3. 评测改成类似 SWE-bench 的 patch 提交方式。
  4. **性能不是 v0 的目标。** v0 可以是一个很慢、但架构正确的引擎。CUDA graph 必须实现，decode 阶段默认开启。
  5. **v0 不开源。** 要等优化过、反复测试过、足够成熟之后再开源，到那时再和 DeepInfer、vLLM 做性能对比。
  6. 版本切换不做新旧版本交替执行，改为排空加超时中止；v0 不限制读取环境变量；DS 的视觉编码器推迟到 v1；鉴权等能力在后续版本再加。
  7. **去掉热、温、冷三档。** 改为按 Cordis 的原则，从实际变化推导出最小的动作计划（4.5）；排空改为按需；调用方只有 `--dry-run`。

## 0. 一句话

v0 是一个**架构正确、所有变更路径都能端到端走通的真实推理引擎**：
- 在单台 8×SM100 上，先跑通 Qwen3.8-27B，再跑通 DeepSeek-V4.1-Flash-1017；
- 不写模拟器。快速测试用同一份模型代码，配上参照实现和小尺寸配置；CI 只用一个极简的假执行器测变更机制；
- 开发时，agent 在常驻实例上用 `apply` 自由修改、做实验。要评测时，向评测服务提交一个 patch（相对开发起点的 diff），评测服务打上 patch 后冷启动评测；
- 引擎本体是可部署的推理引擎，RSI 平面是可拆卸的插件；
- **不追求性能**：v0 可以很慢，但架构必须正确。性能优化留给使用者自己的 RSI。

## 2. 设计立场

### 2.1 框架提供机制，不规定 RSI

使用者自带的东西：优化目标、agent 和 LLM、搜索方法、评测套件、门禁。框架保证以下几点：
- **任何改动都能安全地应用和回滚**，并且返回诚实的结果：要么成功应用，附上实际执行的动作计划；要么 `failed`，附上诊断信息，并且已经回滚。`restart-required` 留给将来的策略钩子使用。
- **任何结果都能追溯**到确切的系统身份。
- **评测在候选的边界之外**，并且在冷启动的独立实例上进行。
- **改动可以叠加**：被接受的身份可以成为新的基线，可以分支，也可以合并。

讨论稿里的"两档门禁""策略决策点""kernel 注册表"仍然保留，但它们的角色是**默认插件和加速路径**，不是 RSI 的边界。

### 2.2 引擎本体就是产品

- 引擎本体（前端、内核、执行层）单独就能部署，地位和 vLLM、SGLang 相同。
- **引擎源码树**指系统身份覆盖的那部分代码：`core`、`policies`、`models`、`kernels`、`executors`、`platforms`、`frontend`。快照和 change-set 都只针对它。
- RSI 平面（评测服务、谱系、发布导出）是引擎源码树**之外**的一个插件包 `rsi/`。它可以和引擎放在同一个仓库里，但不计入引擎身份，也不进入候选快照，所以 patch 改不到它。
- CI 里有一项专门的检查：不安装 `rsi/` 时，引擎仍然能构建、能服务、能通过 `apply` 做运行时调整。
- 运行时调整能力，也就是对任意改动的应用和回滚，由内核的变更机制和 `apply` 入口提供。RSI 平面只是这套机制的另一个调用者。

### 2.3 开发和评测分开

```
agent 工作区 ──apply──► 常驻实例（按推导出的动作调整，随便试，结果只供参考）
     │
     └─ submit(起点身份, patch, 套件) ──► 评测服务
           1. 校验：起点存在、受保护路径、静态检查
           2. 物化：起点快照 + patch → 候选快照（得到候选身份）
           3. 冷启动：在评测服务启动时被指定的 GPU 上，分别启动起点和候选
           4. 运行套件：门禁 + 评分（性能默认成对测量）
           5. 结果写入谱系：(起点, patch, 套件版本) → 结果
```

- **常驻实例**：agent 启动后一直运行，接受 `apply`，用来观察"改了什么、行为变了什么"。它被反复热 patch 过，性能数字依赖 patch 历史，也会受预热状态影响（KV 命中、JIT 缓存），所以结果只供参考。
- **评测服务**：只接受 patch，自己持有起点快照，每次都冷启动。"这个改动是不是真的更好"只能由它回答。
- 这样做的好处：
  - **信任边界清楚**：评测服务确切知道改了什么，可以直接审查 diff。SEIS 里"省略约 39% 词表行"的问题，最后就是靠代码审计才发现的。
  - **天然隔离热 patch 的历史**：只在被热 patch 过的进程里成立的改动，冷启动时会暴露出来。
  - **和身份 DAG 对齐**：patch 就是 DAG 上的一条边。
  - **对 agent 没有要求**：任何会改文件的 agent 都能产出 diff。
- `apply` 和评测共用同一种 change-set 格式（4.6），区别只在于打到哪里：`apply` 打到正在运行的实例上，由框架推导动作计划；评测服务打到干净的起点快照上，只走冷启动。

### 2.4 一切改动都允许，动作由框架推导

- agent 可以改任何文件。框架根据改动落在哪些节点，沿依赖图推导出需要的最小动作，然后执行（4.5）。
- **清单是声明，验证靠静态检查和运行时守卫。** agent 少报依赖换不来更便宜的动作，只会得到 `failed` 和诊断信息。
- 在契约包络内的改动走快路径；包络外的改动走慢路径，同样受支持，并记入包络失效日志。

### 2.5 不写模拟器：测试分四层

| 层 | 跑在哪里 | 用什么 | 用来测什么 |
|---|---|---|---|
| CI | 任意机器，CPU 即可 | **极简假执行器**：没有任何模型语义，只按 plan 走流程，可以注入延迟和故障 | 变更路径、两阶段提交、版本切换、回滚、静态检查、拆除检查 |
| 快速测试 | 单张 SM100 | 同一份模型代码，加小尺寸配置和 PyTorch 参照 solution | 机制和正确性；参照模式（批量对单条）；植入缺陷 |
| 截断模型（可选） | 一张或几张 SM100 | 真实权重的前若干层，加真实 kernel | 快速内循环：性能和机制都是真的，只是输出质量没有意义 |
| 全模型 | Qwen3.8：1–4 张卡；DS 1017：整台 8 卡 | 真实权重，加真实 kernel | 最终评测和部署 |

- 假执行器必须保持极简：**只要往里面加模型语义，它就会重新变成模拟器**。它只负责"让 plan 跑起来"，比如按声明的 shape 分配 buffer、按配置延迟、在指定位置注入故障，输出没有意义。
- 参照 solution 本来就必须写：D6 要求每个 definition 都有兜底 solution，D10 的参照模式也要用它。所以快速测试这一层不需要额外实现。参照 solution 一律按请求、按 token 顺序计算，所以天然 batch-invariant，结果也和 chunk 切分方式、graph 分桶时的 padding 无关。

### 2.6 不追求性能：只实现"对架构提出要求"的东西，而且只做最简正确版本

判断一个特性要不要进 v0，看它会不会对状态、plan 或变更机制提出新的要求，而不看它能不能让引擎更快：
- **对架构提出新要求的特性**：v0 要实现一个最简单的正确版本，用来证明架构装得下它。不调优，也不追求它带来加速。
- **只影响快慢、不对架构提出新要求的优化**：v0 一律不做，留给使用者的 RSI。架构要保证这些优化将来可以作为普通改动加进来。

按这条规则的划分（已确认）：

| 特性 | 归类 | v0 的做法 |
|---|---|---|
| 前缀复用 | 对架构有要求：命中规则、快照、跨层借用 | 最简单的按块哈希匹配，不做淘汰策略调优 |
| CUDA graph | 对架构有要求，而且真实部署都会用：静态 buffer、冻结的绑定、kernel 必须能被 capture、显存池，以及它和双缓冲 plan、跨进程共享显存、版本切换之间的交互 | **必须实现，decode 阶段默认开启**，包括固定长度的投机验证。分桶用最简单的固定方案（例如 2 的幂）；失效和 recapture 由 P3、P5 测试。不调优分桶；prefill 先用 eager |
| 投机解码 | 对架构有要求：verify 阶段的 plan、被拒 token 的 KV 和 recurrent state 回滚 | 实现一种固定长度的最简版本，不做变长验证 |
| EP 和 EPLB 重排（DS） | 对架构有要求：权重按 EP 分片、运行时迁移权重 | EP8 加最简单的周期性重排 |
| 融合组 | 对架构有要求：融合是显式单元 | 只有机制，默认不做任何融合 |
| 权重原地替换（refit） | 对架构有要求：布局和地址不变时只换内容；依赖权重数值的派生量要重算 | 实现同一模型、同一布局下的权重替换 |
| KV 池扩容（grow） | 对架构有要求：地址不变，graph 才能保持有效 | 启动时预留虚拟地址，按需映射物理显存；只做扩容，不做缩容 |
| LoRA | 对架构有要求：adapter 池，以及按 adapter 区分的 KV | v0 不实现，只在 M0 的纸面包络测试里检验设计能装下它 |
| 异步（重叠）调度 | 只影响快慢 | 不做；契约里把快照时效作为一个声明属性，将来可以加 |
| 调度策略（chunk 预算、准入、抢占、负载均衡） | 只影响快慢 | 默认用最简单的版本：FCFS 加固定 chunk |
| kernel 融合和手写的快 kernel | 只影响快慢 | 不做；默认绑定现成 kernel 库里最直接的实现，参照 solution 始终可用 |
| graph 分桶调优、通信重叠、CPU 开销优化 | 只影响快慢 | 不做 |

如果 v0 慢到快速测试或评测在合理时间内跑不完，就只针对那一个瓶颈做最小的改动，不做系统性的优化。

## 3. 范围

### 3.1 v0 包含

- 引擎本体的全部机制（第 4 节）。
- 两个模型的声明式规格和真实实现：先 Qwen3.8-27B，再 DS 1017（第 5 节）。
- `cuda-sm100` 平台插件，以及 CI 用的 `fake` 平台。
- 每个 definition 的 PyTorch 参照 solution，以及真实 kernel 的绑定。
- OpenAI 兼容的前端，以及 tokenizer/encoder 进程。
- RSI 平面：评测服务、谱系、发布导出。
- 第 6 节列出的全部路径，以及第 7 节列出的全部植入缺陷测试。

### 3.2 v0 不包含

- 多节点、P/D 分离、跨节点 EP。接口按可扩展的方式设计，但不实现。
- 不停服务的在线重分布：例如 Elastic EP 式的专家迁移，或者权重在 rank 之间重新切分。v0 里改并行配置是靠重建 rank 进程来完成的（例如 TP4 改 TP2，见 4.5）。
- LoRA：v0 不实现，但状态和动作的设计要能装下它。
- 鉴权、角色、线上和开发的区分、发布签名。
- 强隔离（容器、独立用户）。v0 只做到进程和路径级别的分离。
- 在 CPU 上执行模型；除 SM100 以外的硬件。
- 性能目标和性能优化（见 2.6）。评测服务必须**能测**性能，因为使用者的 RSI 会用到；但 v0 引擎自身的性能不设目标。
- 开源发布，以及和 DeepInfer、vLLM 的性能对比。这两件事等引擎优化成熟以后再做。
- 资源分配和调度：集群层面的 GPU 分配、多实例编排、评测排队的公平性，都不归引擎管。
- 多模态：v0 只做文本生成。DS 1017 的视觉编码器推迟到 v1。
- 新旧版本交替执行或同时执行。

### 3.3 目标形态

| 顺序 | 模型 | 硬件 | 并行 | 正确性参照 |
|---|---|---|---|---|
| 1 | Qwen3.8-27B | 单台 8×SM100（sm_100，每卡约 180 GB，节点内 NVLink 全互联） | TP1，以及一种多 rank 配置（TP2 或 TP4，M0 选定），用来测跨 rank 事务 | HF 参照实现；vLLM 的输出 |
| 2 | DeepSeek-V4.1-Flash-1017 | 同上 | attention DP8 + MoE EP8，prefill 和 decode 混跑 | DeepInfer 的输出（batch-invariant 模式） |

这里的并行配置是"把模型放进硬件、并测到多 rank 路径"的最低要求，不是为了性能选的。

先做 Qwen3.8 的理由：
- TP1 就能放进单卡，一台节点可以同时跑 8 个实例，适合早期把各条路径跑通；
- 它的状态种类（recurrent state、conv state）能直接压测 D4。

DS 1017 的每个实例要占满整台节点，并发很低，环境前提也更多，所以放在第二步。

## 4. 架构

### 4.1 两部分

```
┌──────────────────────────── 引擎本体（可部署） ──────────────────────────────────────┐
│ 前端：OpenAI server · tokenizer/encoder · detokenizer                               │
│ 内核：控制面（变更事务 · apply 与控制 API · 身份 · 自省） · 调度宿主（机制 + 策略单元）│
│       每 rank：状态进程（权重 · 异构状态池） + worker 逻辑进程（plan · kernel · 执行）  │
│ 平台：cuda-sm100 · fake（只用于 CI）                                                 │
└───────────────────────────────────────▲──────────────────────────────────────────────┘
                                        │ 只通过公开的控制 API
┌──────────────────────────── RSI 平面（可拆卸） ─────────────────────────────────────┐
│ 评测服务（patch 校验 · 物化 · 冷启动 runner · 套件插件）                                │
│ 谱系（身份 DAG · 事件日志） · 发布导出                                                │
└──────────────────────────────────────────────────────────────────────────────────────┘
```

### 4.2 进程拓扑

| 进程 | 数量 | 承载的模块 | 重启的影响 |
|---|---|---|---|
| 前端 | 1 个或多个 | `frontend.*` | 只影响连接，引擎不受影响 |
| 控制面 | 1 | `core.change`、`core.identity`、`core.api`、`core.introspect`、`core.supervisor` | 重启控制面就是重启引擎（变更机制本身变了）；谱系和事件日志在磁盘上保留 |
| 调度宿主 | 1 | `core.sched`、`policies.*` | 可以单独重启：rank 进程和状态都保留，靠请求日志恢复在途请求 |
| 状态进程 | 每 rank 1 个 | `core.state.holder` | 重启会丢失它持有的权重和状态，需要重新加载 |
| worker 逻辑进程 | 每 rank 1 个 | `core.plan`、`core.kernels`、`core.dist`、`models.*`、`executors.*` | 可以单独重启：重新映射状态进程持有的显存，重建 plan、graph 和通信组 |
| 评测服务 | 由人按需启动，可以有多个 | `rsi.evalsvc` | 独立进程，代码不在引擎源码树里；在启动时指定的 GPU 上拉起被测实例；不影响引擎 |
| 谱系服务 | 1 | `rsi.lineage` | 不影响引擎 |

要点：
- **状态进程和 worker 逻辑进程分离**，这是"状态比逻辑活得长"的具体形式：状态进程持有权重和 KV 所在的显存，通过 CUDA IPC 或 VMM 导出句柄，交给 worker 逻辑进程映射。
  - 去掉模拟器之后，这件事在 v0 就必须在真实 GPU 上成立，所以放在 M1 先做可行性验证（第 8 节）。
  - 如果做不成，重启 worker 逻辑进程时就得连同状态进程一起重启，重新加载权重。动作推导会照实反映这一点，架构的其余部分不受影响。
- 调度宿主和 worker 之间的每步通信走共享内存通道。控制消息走单独的 RPC 通道。

### 4.3 模块与依赖

下表最后一列是按 4.5 的规则推导出来的**默认动作**，不是手工声明的。实际执行的动作，还取决于改动的种类：只改内容、改布局、改代码，还是改拓扑。

| 模块 | 所在进程 | 层 | 主要依赖 | 改动后的默认动作 |
|---|---|---|---|---|
| `core.context`、`core.manifest`、`core.identity`、`core.change`、`core.ipc`、`core.supervisor`、`core.api` | 控制面（其中一部分在各进程里都有） | 机制 | 彼此之间，以及 platform | 重启引擎：变更机制本身变了 |
| `core.state.holder` | 状态进程 | 机制 | ipc、platform | 重启受影响的 rank 进程，重新加载权重 |
| `core.state.kinds` | 状态进程、worker | 机制 | state.holder | 接口不变的实现改动：重启 worker 逻辑进程；布局变化：迁移或失效 |
| `core.dist` | worker | 机制 | ipc、platform | 重启 worker 逻辑进程，重建通信组 |
| `core.plan`、`core.kernels`（注册表） | worker | 机制 | kernels、models、state.kinds | 重启 worker 逻辑进程，重建 plan 和 graph |
| `core.sched` | 调度宿主 | 机制 | ipc，以及状态服务的 API | 重启调度宿主，靠请求日志恢复在途请求 |
| `core.introspect` | 各进程 | 机制 | — | 重启所在进程 |
| `policies.*` | 调度宿主 | 策略 | 调度决策点接口 | 重新绑定，epoch 边界生效 |
| `models.qwen38`、`models.ds_v41_flash` | worker | 模型 | kernel definitions、state.kinds | 在进程内重建 plan 和 graph；默认认为 KV 数值可能变了，KV 和前缀缓存失效，排空受影响的请求（模块可以声明"不改变 KV 数值"来避免）；改状态规格时走迁移或失效 |
| `kernels.reference.*`、`kernels.solutions.*` | worker | kernel | definitions、外部 kernel 库 | eager 路径上重新绑定；graph 里的重建受影响的 plan 和 graph；外部库版本变化时重启 rank 进程 |
| `executors.cuda`、`executors.fake` | worker | 执行层 | platform | 重启 worker 逻辑进程 |
| `platforms.cuda_sm100`、`platforms.fake` | 全部 | 平台 | — | 重启引擎 |
| `frontend.*` | 前端 | 前端 | 引擎客户端 API | 只重启前端 |
| `rsi.*` | RSI 平面各进程 | RSI | 只依赖公开 API | 不影响引擎 |

依赖方向的硬约束，由静态检查强制：
- `core.*` 不能 import `rsi.*`、`policies.*`、`models.*` 的具体实现，只能依赖它们实现的接口。
- 引擎和评测服务互相不 import，只通过公开 API 交互。
- 只有 `core.plan` 能做 CUDA graph capture；只有 `core.state` 能直接访问状态存储；只有 `core.context` 的配置服务能读取配置文件和声明过的配置键。环境变量 v0 不限制。

### 4.4 模块清单

每个模块目录下放一份清单，例如：

```toml
[module]
id = "policies.prefill_chunk_budget"
layer = "policy"            # mechanism | policy | model | kernel | executor | platform | frontend | rsi
process = "scheduler"       # 由哪个进程承载

[provides]
decision_points = ["sched.chunk_size@1"]

[requires]
services = ["sched.snapshot@1"]
config = ["sched.chunk.max_tokens"]   # 只能读取声明过的配置键

[binding]
time = "per_step"           # per_call | per_step | per_plan | startup

[state]
owns = [{ kind = "policy_state", layout = 1, migrate = "migrate_v0_to_v1" }]

[contract]                  # 可选
reference = "policies.prefill_chunk_budget:reference"
tests = ["tests/contract_chunk_budget.py"]
```

- 清单中没写的服务、配置、状态，运行时一律拿不到，访问时由 context 直接抛错。
- 静态检查在 CI、`apply` 和评测服务校验时都会跑：
  - import 图必须是 `requires` 的子集；
  - 禁止模块级可变全局状态；
  - 禁止在 `core.plan` 之外做 capture；
  - 禁止引擎和评测服务互相 import。

### 4.5 影响传播与动作推导

v0 不把改动分成热、温、冷三档。框架从"改了什么"出发，推导出"哪些东西要替换、重建或重启"，只动真正受影响的部分，和 Cordis 只重载受影响的插件子树是同一个原则。不同改动的调整开销不同，这是设计如此。

**资源依赖图**。节点分五类：
- 代码模块；
- 配置键；
- 状态对象：权重、KV 池、recurrent state、adapter、策略的跨步状态；
- 派生产物：plan、CUDA graph、通信组、依赖权重数值的派生量（例如量化 scale）、实测的性能曲线；
- 进程。

边有两个来源：模块清单里的声明（requires、state、binding、所在进程），以及框架自己记录的派生关系，例如一个 plan 依赖哪些模块、solution、状态布局和 buffer 地址。

**每类节点声明自己支持哪些调整动作**。下表大致从便宜到昂贵排列：

| 动作 | 含义 | 例子 |
|---|---|---|
| 无 | 不受影响 | — |
| 重新绑定 | 换一个实例或实现，地址和布局都不变 | 策略单元；eager 路径上的 kernel solution |
| 原地替换（refit） | 只换内容，布局和地址不变 | 同一模型的新权重 |
| 扩容（grow） | 只增加容量，已有地址不变 | 扩大 KV 池 |
| 重建派生产物 | 重新编译 plan、重新 capture graph、重建通信组、重算依赖权重数值的派生量 | graph 里的 kernel 换了 |
| 迁移 | 按迁移函数把状态从旧布局转到新布局 | 带迁移函数的状态布局变化 |
| 失效 | 丢弃，需要时重算 | 换权重以后的 KV 和前缀缓存 |
| 重启进程 | 重启节点所在的进程，进程里的所有节点都受影响 | 调度机制的代码；状态进程的代码 |
| 重启引擎 | 整个引擎从快照重启 | 控制面或变更机制本身的代码 |

**推导规则**：
1. 从变化的节点出发，根据变化的种类（只改内容、改布局、改代码、改拓扑），选出这个节点支持的、最便宜的动作。
2. 如果这个动作改变了下游节点依赖的东西（版本、布局、地址或数值），就沿依赖边继续传播。
3. 如果某个节点不支持所需的动作，就升级到它所在的进程。进程重启又会影响它承载的所有节点，继续传播。
4. 推导不出来的情况，例如清单里没有声明的变化种类，一律保守处理，升级为重启所在进程。
5. 每个动作还要声明会不会影响在途请求。只有会影响的动作，才让受影响范围内的请求排空（4.8）。

**结果是一份动作计划**，列出：对哪些节点执行什么动作、原因是什么；要启动或停止哪些进程；哪些状态和派生产物失效；要不要排空、排空哪些请求。`apply --dry-run` 只返回这份计划，不执行。v0 不提供"禁止某些动作"的参数：agent 想控制代价时，先看计划，再决定要不要 apply。

**例子**：

| 改动 | 推导出的动作 | 不动的部分 |
|---|---|---|
| 替换无状态的策略单元 | 在调度宿主里重新绑定，epoch 边界生效；不排空 | 其他一切 |
| 运行时可变的配置键，新值在启动上限内 | epoch 边界生效；不排空 | 其他一切 |
| 配置键超出启动时定下的上限 | 按配置键声明的动作，例如 graph 最大尺寸变大时重新 capture | 由声明决定 |
| eager 路径上的 kernel solution | 重新绑定 | 其他一切 |
| graph 里的 kernel solution（同一 definition，声明为精确） | 后台重建受影响的 plan 和 graph，epoch 边界切换；不排空，KV 保留 | 进程、权重、KV |
| 模型代码 | 在进程内重建 plan 和 graph；默认让 KV 和前缀缓存失效，并排空受影响的请求 | 进程、权重 |
| 调度机制的代码 | 重启调度宿主，靠请求日志恢复在途请求；不排空 | rank 进程、权重、KV、plan |
| worker 逻辑的代码 | 重启 worker 逻辑进程，重新映射状态进程持有的显存，重建 plan、graph、通信组；在途请求在切换后继续 | 状态进程、权重、KV |
| 同一模型的新权重（shape 和布局不变） | 排空；原地 refit 权重；KV 和前缀缓存失效；重算依赖权重数值的派生量 | 进程、plan、graph、通信组 |
| 新增 LoRA（v0 不实现，只用来检验设计） | 加载到 adapter 池的空位；不排空 | 其他一切 |
| 替换已有的 LoRA（同上） | 只排空用这个 adapter 的请求，只让它对应的 KV 失效 | 其他 adapter 和它们的请求 |
| 扩大 KV 池 | grow：映射新的物理显存，分配元数据加上新的块；不排空 | 进程、plan、graph、在途请求 |
| 改并行配置（例如 TP4 改 TP2） | 排空；停掉并重建所有 rank 进程；按新的切法重新加载权重（v0 没有重新切分权重的迁移函数）；重建 KV 池、通信组、plan、graph；调度宿主按新的 rank 拓扑重新配置 | 控制面、前端、谱系 |
| 状态进程的代码、外部 kernel 库或 native 扩展 | 重启受影响的 rank 进程，重新加载权重；排空 | 控制面、前端 |
| 控制面、变更机制本身或平台插件的代码 | 重启引擎 | 磁盘上的谱系和事件日志 |
| 前端代码 | 只重启前端 | 引擎 |
| 清单和代码不一致 | 返回 `failed` 和诊断信息，不执行任何动作 | 一切 |

### 4.6 change-set（patch）格式

`apply` 和评测服务消费的是同一种对象：

```
change-set
  base:      起点身份
  files:     路径 → 新内容的 hash（删除记为 null）；另附 unified diff，只用于展示和审查
  config:    配置键 → 新值
  deps:      依赖锁文件的变化
  artifacts: 名称 → 内容 hash（预编译 kernel、校准数据等大产物放在内容寻址的 blob 存储里）
  meta:      提交者（自报）、意图说明、证据链接
```

- **应用必须是确定的**：候选身份 = f(起点身份, change-set)。按文件内容整体替换，不用模糊匹配的 diff 打补丁，所以不会出现"打上了但内容不一样"。
- `apply` 不带 change-set 参数时，框架自动计算"工作区相对当前运行身份"的 change-set。
- 评测时提交的 change-set，起点是**开发开始时的版本**，不是常驻实例当前的版本。所以 agent 在开发过程中做的多次 `apply`，在评测服务看来就是一个合在一起的 patch。生成方式：`engine changeset --base <起点身份> --source <工作区>`。

### 4.7 `apply` 的变更流程

1. **生成 change-set**：计算工作区相对当前运行身份的 change-set，得到候选身份。启用 RSI 平面时，快照同时写进谱系仓库。
2. **静态阶段**：校验清单，检查 import 图，跑 lint 规则。不通过就返回 `failed`，旧版本继续服务。这相当于 Vite 的 error overlay。
3. **影响传播**：按 4.5 推导出动作计划。带 `--dry-run` 时，到这里就返回计划。
4. **策略钩子**：v0 默认全部放行。将来的鉴权、线上和开发的区分、只接受签名产物等规则，都从这个钩子接入；被拒绝时返回 `restart-required` 或 `failed`。变更流程本身不需要改。
5. **准备**：能在不打扰当前版本的前提下完成的动作，先在后台做，当前版本照常服务。例如新建进程、新的 plan 和 graph、新加载的 adapter。
   - 这一步同时是两阶段提交的 prepare 阶段。任一参与者失败，就整体 abort，丢弃已经准备好的东西，当前版本继续服务。
   - 有些动作没法在后台准备，就推迟到排空以后再做。例如：显存放不下第二份资源；或者要重启的正是当前在服务的进程，比如改 TP 时的 rank 进程。
6. **排空**：只有计划里有"影响在途请求"的动作时才排空，而且只排空受影响范围内的请求（4.8）。
7. **执行并提交**：执行推迟下来的动作（停止或重启进程、refit、失效），然后在 epoch 边界 commit。
   - 除非改的就是控制面和前端自己的代码，它们在整个过程中都保持运行。新到达的请求在前端排队，不会丢。
   - 排队有上限，超过就返回 503 加 `Retry-After`。排队上限和排空超时都可以配置。
8. **恢复服务**：新版本开始处理排队中的请求。
9. **返回结果**：新旧身份；实际执行的动作计划；各阶段耗时，包括排空耗时、被中止的请求数、重启了哪些进程；诊断信息。结果同时写入事件日志。

### 4.8 版本切换语义

- 每个请求都带着系统身份。**同一时刻只有一个版本在执行**，不做新旧版本交替执行，也不让两个版本同时执行。原因：新旧版本可能连并行方式都不同，例如 TP4 和 TP2；交替执行就要同时维护两套权重布局、两套 KV 布局，复杂度太高。
- **按需排空**：
  - 计划里没有"影响在途请求"的动作时，新版本在下一个 epoch 边界直接生效，在途请求继续跑。例如：换无状态策略、扩大 KV 池、新增 adapter、重启调度宿主。
  - 有这类动作时，只排空受影响范围内的请求。例如：换权重、改 KV 布局、重建 rank 进程、改模型代码。旧版本不再接受这类请求，受影响的在途请求继续跑完，新到达的请求排队。
  - 排空超时可配置，默认 10 秒。超时后中止剩余的受影响请求，返回明确的状态码，说明是"因版本切换中止"。
- **响应里的身份**：HTTP 头 `x-engine-identity` 和流式响应的首个事件里，写请求开始时的身份。请求中途跨过了版本切换的，在最后一个事件里列出它经历过的全部身份。

### 4.9 系统身份

身份是对下列内容的 hash。各部分同时以清单的形式保存，便于 diff，change-set 就是对这份清单的 diff：
- 每个模块的源码内容 hash，以及模块清单；
- 所有声明过的配置键的生效值。环境变量 v0 不限制读取，也不计入身份；评测服务冷启动被测实例时，使用一组固定的环境变量，并把它记在评测结果里；
- 依赖锁文件：Python 包、外部 kernel 库、native 库；
- 模型规格，以及权重清单（文件名、大小，能拿到时加上文件 hash）；
- 平台插件、GPU 型号、驱动版本、CUDA 和编译器版本；
- 各状态种类的布局版本；
- kernel 绑定表（definition → solution）；
- 内容寻址的产物（artifacts）。

### 4.10 状态服务

**状态种类插件的接口**。在讨论稿 D4 的基础上，吸收了 DeepInfer 的经验：
- `allocate` / `free`，并参与**联合准入**：任一种状态分配不出来，请求就不准入；
- `slice_prefix`；
- `snapshot`：要声明对齐粒度；
- `transfer`：为将来的 P/D 分离预留；
- `invalidate(version)`：**必选**；
- `migrate(old_layout → new_layout)`：可选；
- `refit`：可选。布局和地址不变，只替换内容，例如同一模型的新权重；
- `grow`：可选。只扩容，已有地址不变。KV 池在启动时预留一段虚拟地址，再用 CUDA VMM 按需映射物理显存；
- `hit_rule`：命中时的对齐粒度，以及缺失时怎么回退；
- `rebuild`：缺失时精确重算还是近似重建，近似重建必须声明为"影响输出"；
- 归属：自有，或者**借用另一层的状态**（DS 1017 的跨层 KV 共享需要，见 5.2）。

**权重存储**：
- 从 safetensors 加载，按逻辑名寻址，带版本；
- 布局描述符把每个张量描述成"逻辑坐标到分片"的映射：Qwen 按 TP 切分；DS 的专家按 EP 切分，attention 按 DP 复制；
- 权重所在的显存由状态进程持有，worker 逻辑进程重启时只需要重新映射；支持 refit。

**分配元数据**（空闲表、block table、前缀索引）由状态服务持有，不在调度宿主里。调度宿主只通过状态服务的 API 申请和释放，所以它重启时不会丢失分配状态（P4 依赖这一点）。

**状态不变量**，每个 epoch 检查一次：
- 空闲块加占用块等于总块数；
- 没有重复分配；
- 释放后不能再读；
- 每个请求最终都会释放它的全部状态。

### 4.11 plan 编译器与 kernel 注册表

- **注册表的 schema 和 flashinfer-bench 对齐**（Definition、Solution、Workload、Trace），这样已有 kernel 评测工具（例如基于 flashinfer-bench 的 kernel gateway）产出的 solution，可以直接注册进来。
  - **definition**：语义 id、固定轴和可变轴、dtype、布局、容差、是否 batch-invariant、**PyTorch 参照实现（必选）**。
  - **solution**：目标架构、DSL、依赖的外部库和版本、能否被 capture、是否 batch-invariant、workspace 大小、**shape 约束**。例如 FlashMLA 只支持 64 或 128 个 head：小尺寸配置不满足约束时，自动退回参照 solution，并在结果里标注。
  - **路由**：按 definition 和 shape key 选 solution，在 plan 编译时解析进 plan；eager 路径逐次查表。支持 shadow 和 canary 绑定。
- **plan**：每个（模型，阶段，分桶）一个 plan，阶段包括 prefill、decode、verify 等。plan 由有序的算子、绑定好的 solution、buffer 和 stream 组成。
  - **CUDA graph 只能由 `core.plan` capture。** v0 的 decode 阶段默认使用 CUDA graph（见 2.6）。
  - **依赖记录**：每个 plan 记录自己依赖的模块版本、solution id、参数、状态布局和 buffer 地址。refit 和 grow 不改变地址，所以 graph 仍然有效。**运行时守卫**在每次 replay 前检查这些依赖是否和当前身份一致，用来发现"换了 kernel 却没有 recapture"。
  - 双缓冲：新 plan 在第二个 buffer 里 capture，到 epoch 边界提交。
  - 融合组是显式的单元。
- **派生产物**（例如实测的吞吐曲线、策略的校准数据、依赖权重数值的量化 scale）同样挂在依赖图上，随 plan 和 solution 一起失效。这是对 DeepInfer `DecodePerfCache` 问题的修正。

### 4.12 调度：机制与决策点

**机制**（`core.sched`）：
- 请求状态机；
- 通过状态服务做联合分配；
- 判断 batch 是否合法：版本一致、容量够、有可用的 plan 分桶；
- 执行抢占；
- 多 rank 协调：Qwen 的 TP 组同步推进；DS 的 attention DP8 和 MoE EP8 要求各 rank 同步推进，没有请求的 rank 跑空 batch；
- 同步调度：v0 不做异步（重叠）调度（见 2.6）。但快照的时效是快照上的一个声明属性，将来有人把异步调度作为改动加进来时，策略可以通过这个属性知道自己看到的是 N−1 步的状态；
- **请求日志**：只追加，并且持久化。调度宿主重启后靠重放日志恢复，不需要排空。

**决策点**（`policies.*`，输入是只读快照，输出是决定，由机制校验）：
- 准入和 DP 路由、排序；
- chunk 预算；
- 抢占对象；
- 投机解码的验证长度：支持"CPU 定预算、设备侧定每个请求的长度"的两段式；
- graph 分桶；
- 缓存淘汰；
- EPLB 的触发和重排方案（DS）。

v0 自带的默认策略都是最简单的正确版本：FCFS 准入，固定 chunk，抢占最新到达的请求，固定长度的投机验证，前缀缓存按 LRU 淘汰。DeepInfer 那些按时间预算反解 chunk、DSpark 变长验证之类的策略，不写进基线，留给使用者的 RSI。

### 4.13 CI 用的假执行器

- 输入是 plan，输出没有意义。它按声明的 shape 分配 buffer，按配置的耗时 sleep，在指定的算子、rank 或阶段注入故障（例如异常、挂起、prepare 失败）。
- 只用来测机制：变更路径、两阶段提交、版本切换、回滚、请求日志重放、静态检查、拆除检查。
- **不允许往里面加模型语义。** 需要验证正确性的测试，一律放到快速测试层，在 SM100 上用参照 solution 跑。

### 4.14 前端与部署路径

- OpenAI 兼容的接口：`chat/completions`、`completions`、流式输出。
- tokenizer/encoder 进程：Qwen3.8 用 HF tokenizer 加 chat template；DS 用 deepseek-recipe（MIT，Rust 实现，带 Python 绑定）。detokenizer 单独一个进程。
- 每个响应都带系统身份。

### 4.15 `apply` 与控制 API

v0 不区分线上和开发，也不做鉴权，每个引擎实例都一样：
- **启动**：`engine serve --source <工作区或 commit> --model qwen38|ds1017`，同时提供 OpenAI 端点和控制端点。启用 RSI 平面时，启动用的快照和之后每次 `apply` 的快照都会写进谱系，这样开发起点才能在评测时作为 `--base` 使用。
- **控制命令**：`apply [--source <path|commit>] [--dry-run]`、`status`、`introspect`、`logs`。`apply` 返回 4.7 第 9 步的结果；`--dry-run` 只返回动作计划。
- **改动不限类型**：参数、策略单元、kernel 绑定、模型代码、调度机制、权重、KV 池大小、并行配置、EPLB 重排，都走同一个变更流程。
- 拆掉 RSI 平面之后，这些命令照样可用。
- 控制端口默认只监听本机。
- **常驻实例由 agent 自己管理**：用自己拥有的 GPU 启动、终止、更新多少个都可以。引擎不做资源分配，也不记录有哪些常驻实例。
- 后续版本再通过策略钩子加上：鉴权、线上和开发的区分、按改动类型的白名单、只接受签名的发布产物。

### 4.16 评测服务

- **提交**：`eval submit --base <起点身份> --patch <change-set> --suite <套件@版本>`，立即返回任务 id。查询用 `eval result <id>`。
- **校验**：
  - 起点身份必须在谱系里存在；
  - patch 必须能确定地应用；
  - patch 不能碰套件声明的受保护路径。受保护路径在引擎源码树里，例如参照 solution（`kernels.reference.*`）、采样和停止条件相关的代码。评测器本身和参照输出不在引擎源码树里，patch 本来就碰不到；
  - 静态检查必须通过。
  任何一项不通过，就直接拒绝并给出诊断，不占用 GPU。
- **物化和冷启动**：从起点快照加 patch 生成候选快照，在评测服务启动时被指定的 GPU 上冷启动。每次评测都使用全新的进程树和缓存目录。
- **套件**：一个套件 = Workload（请求流或 trace）+ Gates（门禁）+ Scorers（评分）+ Protocol（预热方式、计时区间等）。
  - 任何调用方都可以注册套件，套件带版本，v0 不做权限控制；
  - 套件可以把一部分内容标为隐藏（例如参照输出），隐藏的部分不出现在返回结果里。
- **测量**：
  - 性能默认**成对测量**：起点和候选在同一台机器上交替运行（AB/BA）。套件的 Protocol 可以改成复用缓存的基线，代价是基线和候选不在同一时间、同一机器状态下测得。
  - 正确性的参照输出可以按（身份, 套件版本）缓存。
- **结果**：按（起点, patch, 套件版本）写入谱系，同时附上 diff，方便审查。
- **本地自检**：`engine selfcheck --base <起点身份> --patch <change-set> [--suite ...]`。agent 在自己的资源上，把"起点加 patch"按评测服务完全相同的方式冷启动，跑套件中公开的部分，减少白白排队。
- **资源**：评测服务由人在自己选定的机器上启动，只使用启动时指定的 GPU，收到的任务按提交顺序执行。集群层面的资源分配和调度不归引擎管。
- **内置示例插件**（可选，不强制使用）：
  - 精确参照门禁（批量对单条；候选对起点）；
  - 容差门禁；
  - 停止行为探针；
  - 变化请求序列探针；
  - 生成式质量评测；
  - SLO 约束下的 goodput 评分。

### 4.17 谱系与发布

- **存储**：内容快照放在一个 bare git 仓库里；身份、边（也就是 change-set）、事件、评测结果放在 sqlite 里；大产物放在内容寻址的 blob 存储里。
- **分支**：指向某个身份的命名指针。
- **promote**：只有在**这个确切起点**上评测通过的 patch，才能 promote 到这个起点所在的分支。
- **起点漂移**：基线已经前进时，patch 必须先 rebase 到新基线，得到新的 change-set，再重新评测。merge 也遵循同样的规则：git merge 之后得到新身份，必须重新评测。
- **事件日志**记录：提交者（自报，v0 不做认证）、改了什么、为什么改、证据（链接到测量记录）、实际执行的动作计划、结果。报告里的结论必须链接到产生它的事件，这是 SEIS 的教训：继承下来的报告会把错误结论一起传下去。
- **包络失效日志**是事件日志里的一类事件：记录哪次改动需要修改契约或内核、原因是什么、改了哪个契约。
- **发布**：`release export --identity X` 产出一个发布产物，即代码包加身份清单（v0 不签名）。部署时不需要 RSI 平面。

## 5. 模型规格（同时也是包络测试）

### 5.1 Qwen3.8-27B（第一个）

- 结构：64 层，其中 48 层 GatedDeltaNet，16 层 full attention；BF16 权重约 55.6 GB，TP1 就能放进单张 SM100。
- 各项尺寸以 checkpoint 的 config 为准，在 M0 核对。已知的算子尺寸：gated RMSNorm `[B,48,128]`；causal conv 10,240 个 channel、width 4；recurrent GDN 16 个 key head、48 个 value head，head_dim 128，FP32 状态。
- 实现来源：
  - 语义以 HF 的 modeling 代码为参照；
  - 工程实现参考 vLLM；
  - kernel 来自 flash-linear-attention（GDN）、FlashInfer 或 FlashAttention（attention），以及 kernel gateway 已有的三道题（gated RMSNorm、causal conv decode、recurrent GDN）。
- 需要声明的状态种类：
  - 16 层 full attention 的 paged KV；
  - 48 层 GDN 每个请求的 recurrent state（FP32）和 conv state。要做前缀复用，就必须在块边界打快照。
- 并行：TP1，以及一种多 rank 配置（TP2 或 TP4）。跑多个副本属于资源分配，不归引擎管。
- 投机解码的草稿来源：checkpoint 带 MTP 层就用 MTP；不带的话，用不需要额外模型的 n-gram 草稿。M0 核对。
- 正确性参照：HF 参照实现，以及同一硬件上 vLLM 的输出。

### 5.2 DeepSeek-V4.1-Flash-1017（第二个）

下面的数字来自 HF 上的 `config.json`：
- **主干**：40 层，hidden 5120，64 个 head，1 个 KV head，head_dim 512（其中 RoPE 部分 64），q_lora 1280，o_lora 1024，o_groups 8；词表 129,280；最长上下文 1,048,576（YaRN，factor 16）。
- **attention**：
  - `compress_ratios` 共 43 项，推测是 40 层主干加 3 个 nextn 层，每项取值 0、1、2，对应不同的压缩类型；
  - `sliding_window` 128；indexer 32 个 head，head_dim 128，top-k 512；
  - candidate 选块：源层 20，选 2048 个块，块大小 8。
- **跨层共享**：`kv_source_layer_ids = [2, 8, 14, 20]`，`index_source_layer_ids = [2, 8, 14, 20, 24, 28, 32, 36]`。也就是说，一部分层并不自己产生 KV 或 indexer，而是借用源层的。
- **MoE**：384 个路由专家加 1 个共享专家，每个 token 激活 6 个；intermediate 2304；打分函数 sqrtsoftplus，`noaux_tc`。EP8 下每卡 48 个专家。
- **mHC**：`hc_mult` 4，Sinkhorn 迭代 20 次。
- **Engram**：在第 1 层和第 14 层；两张表，各约 3.84 亿行；n-gram 最长 4；8 个 head，head_dim 256。
- **投机解码**：3 个 nextn 层；DSpark 块大小 5，目标层 37–39，draft 侧 128 个专家激活 3 个。
- **视觉编码器**（推迟到 v1，v0 只做文本生成）：32 层，hidden 1024，patch 14，每张图最多 1024 个 token。
- **量化**：FP8 块量化（32×32，ue8m0 scale），专家是 FP4。整个 checkpoint 476 GB，约 7,632 亿参数。
- YOCO 式 encoder/decoder 的分界以 DeepInfer 的 `ModelMetadata` 为准，在 M0 核对。
- **实现来源**：DeepInfer 的模型代码（`v4_modules` 等）和它依赖的 kernel（FlashMLA、DeepGEMM、DeepEP、DeepSelect、TileLang kernel）。
- **环境前提**：
  - DeepInfer 要求 NVCC 13.1 以上，并 pin 了 `torch 2.13+cu132`，驱动兼容性需要先验证；
  - 第三方报告说，即使只跑单机，它也需要 RDMA 设备（Engram 走 NCCL 的 GPU 发起通信）。

需要声明的状态种类：

| 状态 | 粒度 | 特殊之处 |
|---|---|---|
| block KV（main，压缩） | 按 token 分页，128 token 一块 | FP4（per-16 e4m3）；**跨层借用**（`kv_source_layer_ids`） |
| indexer K | 按 token 分页 | MXFP4；跨层借用（`index_source_layer_ids`） |
| 每序列 state slot | 按请求 | SWA 环形缓冲区（窗口 128，加投机回退的余量）和压缩边界累加器；分为需要持久化的区域和可丢弃的区域；只在 128 token 边界打快照 |
| nextn 状态 | 按请求 | 3 个 nextn 层的 KV。v0 用 nextn 层做固定长度投机，不用 DSpark 的变长验证 |
| Engram 表 | 类似权重 | 在 host 内存里，按词表维度切分，经 RDMA 读取 |
| 视觉嵌入缓存 | 按图片 | v1 再做 |

**对 D4 的冲击**：讨论稿 11(1) 把"跨层共享 KV"列为包络外，而 DS 1017 正好用了它。所以状态归属必须支持"借用另一层的状态"。这一条记为包络失效日志的第一条。

## 6. 需要端到端走通的路径（验收场景）

"运行环境"一列：CI 表示用假执行器；快速表示单张 SM100 上的参照实现加小尺寸配置；全模型表示真实权重和真实 kernel。

| # | 路径 | 运行环境 | 验收要点 |
|---|---|---|---|
| P1 | 从一个身份冷启动并开始服务 | CI、快速、全模型 | 前端返回带身份的响应 |
| P2 | 替换策略单元 | CI、快速 | 不重启任何进程，也不排空；新策略在下一个 epoch 边界生效；任何时刻只有一个版本在执行；响应里的身份正确 |
| P3 | 重新绑定 captured graph 里的 kernel | 快速、全模型 | 后台 recapture 后提交；如果人为跳过 recapture，运行时守卫必须拦下 |
| P4 | 修改调度机制代码 | CI、快速 | 交接调度宿主；worker 和状态保留；重放请求日志后，在途请求不丢 |
| P5 | 修改模型代码或 worker 逻辑 | 全模型 | 新的 worker 逻辑进程映射状态进程持有的显存，不重新加载权重；在映射来的显存上重新 capture decode graph，并能正确 replay；记录这一档的实际耗时 |
| P6 | 状态布局变化 | 快速 | 有迁移函数时走迁移；没有时按声明失效（KV）或重新加载（权重） |
| P7 | 修改状态进程或控制面的代码 | CI、全模型 | 状态进程：只重启 rank 进程，控制面和前端不重启，排队的请求不丢；控制面：重启引擎，谱系和事件日志不丢 |
| P8 | `failed` | CI | 静态检查不通过、prepare 失败、某个 rank 故障，三种情况都 abort 并回滚，旧版本继续服务，返回诊断信息 |
| P9 | 跨 rank 事务 | CI、全模型（Qwen 的多 rank 配置，DS 8 rank） | 向第 k 个 rank 注入 prepare 故障，所有 rank 都 abort |
| P10 | EPLB 在线重排（DS） | 全模型 | 在 epoch 边界迁移专家权重；参照模式下前后输出一致 |
| P11 | patch 评测 | 快速、全模型 | 提交（起点, patch, 套件）后，评测服务完成校验、物化、冷启动、成对测量，结果写入谱系并附上 diff |
| P12 | 起点漂移 | CI | 旧起点上评测通过的 patch，不能直接 promote 到已经前进的基线；rebase 并重新评测后才可以 |
| P13 | 受保护路径 | CI | 碰了受保护路径的 patch，在校验阶段被拒绝，不占用 GPU |
| P14 | 本地自检和评测服务一致 | 快速 | 同一个（起点, patch, 套件），自检和评测服务的门禁结果相同，性能差异在噪声范围内 |
| P15 | 谱系 | CI | 并行分支、promote、merge；merge 得到的身份不重新评测，就不能 promote |
| P16 | 发布与部署 | 全模型 | 导出发布产物；在没有 RSI 平面的环境部署；部署后的实例照样可以 `apply` |
| P17 | 拆除检查 | CI、快速 | 不安装 `rsi/` 时，构建、服务、`apply` 都正常 |
| P18 | 同一模型的新权重 | 快速、全模型 | 原地 refit：进程、plan、graph 都不变；KV 和前缀缓存失效；依赖权重数值的派生量重算；受影响的在途请求被排空。把排空超时设得很短时，剩余请求以"因版本切换中止"的状态码结束 |
| P19 | 扩大 KV 池 | 快速、全模型 | 不排空，也不重启任何进程；graph 仍然有效；在途请求继续跑，新容量立即可用 |
| P20 | 改并行配置（Qwen 的 TP1 和多 rank 配置互换） | 全模型 | 只重建 rank 进程，以及它们的状态、通信组和 plan；控制面和前端不重启；排队的请求不丢 |
| P21 | `--dry-run` 和实际执行一致 | CI、快速 | 对每种改动，dry-run 给出的动作计划和实际执行的动作完全一致 |
| P22 | 按需排空 | CI、快速 | 不影响在途请求的改动不会触发排空；跨过版本切换的请求，在最后一个事件里列出它经历过的全部身份 |

## 7. 植入缺陷测试

v0 验证的是**架构**，不是某个 RSI 目标。做法是把已知的缺陷类型逐一植入，确认每一种都会被某个机制发现；发现不了的，要明确记下来，作为缺口。这些测试都在快速测试层运行（参照 solution 天然 batch-invariant），涉及机制的部分同时在 CI 上跑。

有些缺陷需要 v0 本身没有的组件，例如近似重建、派生的性能曲线（按 2.6，它们都属于只影响快慢的优化）。这类缺陷用**测试专用的组件**来植入：一个声明为近似重建的测试状态种类，一个依赖 kernel solution 的测试派生产物。验证的是架构的声明和失效机制，而不是把这些优化加进 v0。

| 植入的缺陷 | 来源 | 应该由什么发现 |
|---|---|---|
| 去掉 EOS / 改变停止行为 | SEIS 案例 2 | 停止行为探针、参照门禁 |
| 新请求复用已经失效的元数据 | SEIS 案例 3 | 变化请求序列加参照门禁 |
| 只计算部分词表 | SEIS 案例 4 | 参照模式下全词表 logprob 比对；审查 patch 的 diff |
| 只测到 prefill 路径 | SEIS 案例 1 | 示例套件必须覆盖 decode；评测协议检查路径覆盖 |
| block table 映射错误 | — | 参照门禁 |
| 非 batch-invariant 的 solution | — | "批量对单条"门禁 |
| 换了 kernel 但没有 recapture | vLLM #61287 | plan 依赖的运行时守卫 |
| 原地替换权重后，依赖权重数值的派生量没有重算 | vLLM #61287（FlashInfer 的 scale 只在首次 forward 时算一次） | 派生产物声明依赖权重数值；参照门禁 |
| 动作推导漏掉了受影响的节点 | — | `--dry-run` 和实际执行的一致性检查；plan 依赖和 buffer 地址的运行时守卫 |
| 未声明的配置键读取 | DeepInfer 的配置面 | 运行时守卫 |
| 改动只在开发环境的某个环境变量下才成立 | — | 评测服务用固定的环境变量冷启动，这类改动会在评测时暴露 |
| 模块级可变全局状态 | nano-vllm | 静态检查 |
| 少报依赖 | — | import 图检查 |
| 派生的性能曲线没有随 kernel 失效（测试专用组件） | DeepInfer `DecodePerfCache` | 依赖图里派生产物的失效 |
| 近似重建改变了输出（测试专用组件） | SWA bounded replay | approximate 标记加参照门禁 |
| 投机解码的 verify 有错 | — | 参照门禁：无损投机必须和不投机时等价 |
| KV 泄漏或重复分配 | — | 状态不变量检查 |
| 调度宿主重启时丢请求 | — | 请求日志重放加不变量测试 |
| 只在被热 patch 过的进程里才成立的改动 | 本项目的 HMR 设计 | patch 评测的冷启动 |
| patch 修改参照 solution 等受保护路径 | Sakana CUDA Engineer | 受保护路径校验；评测器本身不在引擎源码树里，patch 碰不到 |

## 10. 风险

| 风险 | 表现 | 缓解 |
|---|---|---|
| v0 范围明显变大 | 真实后端、两个模型的移植、环境前提都进了 v0 | 先 Qwen3.8 后 DS；不追求性能，默认实现都取最简单的正确版本（2.6）；每个里程碑都产出能运行的东西；DS 的移植以 DeepInfer 为蓝本，尽量机械地搬 |
| 基线偏弱 | 在一个故意做得很慢的基线上，RSI 的改进很容易拿到，但不一定能迁移到成熟引擎（SEIS 的 3.27 倍就是相对弱基线得到的） | 框架本身不受影响，要不要强基线由使用者决定。需要强基线的使用者，可以从一条"已优化"的谱系分支出发，而不是让基线本身变复杂（待确认） |
| 状态进程和逻辑进程分离做不成 | CUDA IPC 或 VMM 的限制、graph 引用跨进程显存的问题、NCCL 重建太慢，导致重启 worker 逻辑进程时也得重新加载权重 | M1 先做可行性验证；按平台降级，动作推导照实反映 |
| 环境前提不满足 | NVCC、torch、驱动版本跟不上 DeepInfer 的要求 | M0 列出核查清单；Qwen3.8 阶段不依赖这些前提 |
| 大尺寸下没有 batch-invariant kernel | Qwen3.8 的真实 kernel 不保证 batch-invariant，全模型上做不到精确的参照门禁 | 精确门禁放在快速测试层（参照 solution）；全模型用容差门禁加生成式质量评测；DS 用 DeepInfer 的 batch-invariant 模式 |
| DS 阶段并发太低 | 每个实例占满一台节点 | 截断模型作为快速内循环；本地自检减少白白排队 |
| 假执行器膨胀 | 有人往里面加模型语义，它慢慢重新变成模拟器 | 4.13 的硬规则：需要正确性的测试一律放到快速测试层 |
| 评测成本翻倍 | 成对测量需要同时跑起点和候选 | 正确性参照按（身份, 套件版本）缓存；只有性能成对测量；套件可以改成复用缓存的基线 |
| 清单负担太重 | 自由修改代码的 agent 频繁拿到 `failed` | 诊断信息要可操作（像 Vite 的 overlay）；新模块可以用模板生成清单；为 agent 单独写使用文档 |
| 被 Python 锁死 | 将来机制层下沉的成本太高 | FFI 边界纪律：机制接口只传可序列化的数据结构，不让 Python 对象穿过边界 |
| 隔离和鉴权太弱 | 只有进程和路径级别的分离；任何能访问控制端口的人都能 `apply` | 在文档里写明；控制端口默认只监听本机；后续版本通过策略钩子加上 |
| 后台准备新版本时的显存开销 | 准备阶段，新版本的 plan、graph、workspace 和旧版本同时占显存 | 实测；显存不够时，动作计划改为排空以后再准备（停顿更长，但仍然正确，见 4.7） |
| 动作推导漏掉受影响的节点 | 该重建的没有重建，结果静默出错 | 推导不出来时一律升级为重启进程；P21 检查 dry-run 和实际执行一致；plan 依赖和地址的运行时守卫；植入"少报依赖"的缺陷 |
| 环境变量不受限制 | 通过环境变量改变行为的改动，在 change-set 里看不出来 | 评测服务用固定的环境变量冷启动并记录；需要被评测的行为，应当写成声明过的配置键 |
