和 v0-plan 4.3 模块表的差别：
  • 粒度从“进程”变成“单元”。每个模块都是单独装卸、单独重载的单元；进程只是装单元的容器。只有框架本体的代码改了，才需要重启引擎。
  • 状态进程并进了 worker 进程。持有显存的状态单元比逻辑单元活得长，所以改 worker 的代码不用重启进程，也就不需要跨进程共享显存。
  • 建议新增 unit.runtime（单元运行时）、core.deps、core.worker、layers.*、moe.*、sched.reqs（请求表）、dist.groups（通信组）。拆出 core.state.alloc（账本，放在调度宿主）、core.state.weights。
  • v0 不做任何安全和权限：去掉策略钩子、控制端口限制、签名。留下的静态检查只是为了让重载能正确工作。
“改代码”和“改内容”是两回事。“改了它的代码之后”指改这个单元自己的实现；“改了它管的内容之后”指改配置值、换权重、扩 KV 池这类改动。改配置的值从来不重启引擎。
一句话：每个模块都是一个单元，单元是管理和重载的最小单位；进程只是装单元的容器。框架本身几乎不带领域概念，没有内建的“调度器”“KV cache”“TP”，这些全是单元。框架只负责把单元拼起来、换下来。

1. 单元是什么（借鉴 Cordis）

Cordis 是 deepseek-harness 底下的插件框架（源码在 vendor/cordis、vendor/hmr）。我们照它的做法定义单元：

  • 声明依赖和提供：每个单元写明自己要用哪些服务、提供什么服务、读哪些配置。单元通过服务名找对方，不直接 import 别的单元的对象。
  • 所有注册都可撤销：注册 kernel、绑定策略、起线程、开 CUDA stream、torch.library 注册……每一项都返回一个撤销函数。卸载单元，就是把这些撤销函数倒着执行一遍。
  • 依赖自动传播：某个服务的提供者被换掉，依赖它的单元自动卸载，等新提供者就绪再自动装上。缺依赖的单元就停在“等待”状态，不报错。
  • 代码重载：文件改了，先按 import 图找出受影响的单元，清掉这些模块的缓存，重新 import，卸掉旧的、装上新的；中途出错就恢复缓存、装回旧的。
  • 配置原地生效：单元可以注册一个钩子，原地接受新配置；没有注册的话，就只重载这一个单元。
  • 关键取舍：被重载的单元自己内存里的东西不保留。要保住的东西必须放在状态单元里。

2. 三类模块

逻辑单元

代码、策略、模型、kernel、调度逻辑、plan 编译……
重载：便宜，自己内存里的东西丢掉也没关系。
多常改：agent 绝大多数改动都落在这里。

状态单元

显存（权重、KV、各种 state）、通信组、请求表、账本……
重载：贵，会丢掉它持有的状态。v0 默认先排空再重建；提供迁移函数的可以不排空。
多常改：很少改代码；它们管的内容（权重、容量）通过状态动作改。

框架本体

单元运行时、变更事务、进程管家、节点代理、配置、进程间传输、平台，一共七个。
改了：重启引擎。
多常改：极少，要人评审。
语言：v0 全部用 Python。节点代理、进程管家、变更事务是独立进程，只通过版本化消息交互，以后可以单独换成 Rust；其余四个和单元在同一个 Python 进程里，只能用 Python。

3. 动作阶梯：从便宜到贵

#动作什么时候用例子
0不动改动不影响任何在跑的东西新增一个还没人用的单元
1原地接受新配置单元注册了配置钩子，键是每步现读的chunk 大小、EPLB 周期
2重载单元单元代码变了；依赖它的单元跟着重载换一个策略、改调度逻辑、改 worker 主循环
3重建派生产物派生产物按值或按地址依赖了变化的东西重录用到新 kernel 的 graph
4状态动作状态单元管的内容变了，由状态单元自己提供的动作处理refit（换权重）、grow（扩 KV 池）、relocate（EPLB 搬专家）、invalidate（让 KV 失效）
5重启进程进程级的东西变了，卸不掉native 扩展（.so）、并行拓扑变了、NVSHMEM 首次初始化、进程崩溃
6重启引擎框架本体变了，或者平台升级单元运行时的代码、torch / CUDA 版本

每次变更由 core.deps 推导出要做哪几级动作；只有会影响在途请求的动作才排空，而且只排空受影响的那部分请求。

4. 让设计足够有表达力的七条原则

⑤ 页的思想实验说明：能不能“只靠新增和替换单元”支持一个新模型，关键不在框架本体，而在单元之间的接口够不够通用。⑥ 页的思想实验又说明：要支持多台机器，框架本体自己也不能假设“都在一台机器上”（P7）。以下七条从 v0 开始就要成立：

原则意思落在哪
P1 用数据描述并行拓扑（mesh：有哪些维度、各多大）、进程拓扑（有哪些进程角色、各装哪些单元）、张量的格式和放置、每层的状态声明，都写成数据，由单元来解释，不在代码里假设。新模型、新并行方式大多只是新数据加新单元。进程管家、通信组、权重存储、状态种类、模型规格
P2 开放记录跨单元传的记录（StepPlan、决策快照、StepResult）不是固定的结构体，由各单元各自贡献分段。新单元加自己的分段，不用改别人。调度逻辑、worker 主循环、决策点
P3 按 rank 索引凡是和 rank 有关的接口都按 rank 索引。TP 只是“每个 rank 都一样”的特例。StepPlan、账本（按调度域分）、决策快照
P4 能力声明单元声明自己支持哪些动作（refit、grow、relocate、原地接受配置）、能不能被录进 graph、需要什么平台能力、会不会改变 KV 数值。框架按声明推导动作，不在框架里写死一张表。所有单元的清单
P5 联合协议几个单元一起决定的事（准入、前缀命中长度、分桶对齐），走“各自给出约束 → 机制合并”的流程，不由某一个单元说了算。账本、分桶决策点
P6 变更来源统一agent 的 apply、配置、单元自己发起的改动（比如 EPLB）、运维操作，都是 change-set，走同一条流程。core.change
P7 位置透明凡是跨进程的东西都不假设在同一台机器：拉起进程走节点代理，通道按两端是否同机选后端（共享内存或 TCP / RDMA），代码从本机按身份物化的快照目录加载，地址和路径来自拓扑数据，事务参与者按“机器 + 进程”寻址。单机只是多机的特例，就像 TP 只是“每个 rank 都一样”的特例。框架本体：进程管家、节点代理、进程间传输、单元运行时、变更事务
P1–P6 主要约束单元之间的接口，以后违反了还能通过“扩展接口”补救；P7 约束的是框架本体，v0 不做的话，以后补就要改本体。所以 P7 在 v0 必须做对，哪怕 v0 只跑一台机器。

5. 比 Cordis 多做的五件事

  1. 只在 epoch 边界换。Cordis 随时可以卸载插件；我们必须等两步之间、worker 循环停下来再换。
  2. 多个进程一起换。同一个 TP / EP 组的所有 rank 必须在同一个 epoch 换上同一批单元，所以还要两阶段提交。v0 做成同步的：所有相关进程停下 → 各自换 → 都成功才继续，有一个失败就全部回滚。
  3. 派生产物要登记依赖。Cordis 只知道“某个提供者换了”。CUDA graph 这类派生产物依赖了什么、怎么依赖的（实时、按地址、按值），要由产物的主人登记给 core.deps，上游变了再通知它重建哪些。
  4. 卸载顺序关系到显存安全。必须先卸用显存的一方（graph、plan），再卸持有显存的一方。Cordis 里多个异步撤销是并发执行的，我们改成按依赖反方向依次卸载。
  5. 跨机器。Cordis 是单进程的；我们的单元分布在多个进程、以后还有多台机器上，所以要有节点代理、按身份分发代码、跨机通道（P7）。

6. 为了让重载可靠，单元要守的规矩

这些规矩不是为了安全，而是为了让“卸掉再装上”不出错，由 core.manifest 静态检查：

  • 不许有模块级可变全局变量；要保住的东西放进状态单元。
  • 所有注册都可撤销，包括 torch.library、线程、CUDA stream、CUDA graph。
  • 通过服务名拿别的单元，不 import 别的单元的对象（否则重载后还拿着旧对象）。
  • 只有 plan 单元能录 graph、能调用 torch.compile。
  • 用到 native 扩展（.so）要在清单里声明，改了它就走“重启进程”。

3. 派生边的“绑定方式”：决定改了以后要不要重建

绑定方式意思例子不用重建就能生效的改动必须重建的改动
实时每次执行都重新读一遍eager 路径上的 kernel、调度参数、采样参数任何改动，下一步就生效无
按地址graph 里记住了“去哪个地址读”权重、KV 池、专家放置表、负载计数、通信 buffer同一个地址、同样的 shape 和 dtype，只改里面的数（refit、EPLB、grow）换了地址，或改了 shape / dtype → 重录
按值录的那一刻的值被写死了graph 里选中的 kernel、标量参数、代码走的分支、分桶大小、DeepEP 模式无任何改动 → 重录
编译器守卫torch.compile 自己会检查、自动重编译—v0 不开 torch.compile，暂时没有这一种
读配置的边也有绑定方式。调度逻辑每步现读的键是“实时”，改了下一个 epoch 就生效；plan 单元编 plan 时读、录进 graph 的键是“按值”，改了要后台重录。改配置值的代价取决于这个键在哪里被读，而不是一律重启。见全景图的场景⑦。

4. 组合规则

规则说明借鉴
① 进程只是装单元的容器进程之间只走三种通道：ZMQ（请求和控制消息）、共享内存（每步的记录）、RPC（变更事务）。显存不跨进程共享，因为状态单元和用它的逻辑单元在同一个进程。mini-sglang 的 ZMQ + 消息 dataclass；sglang 的 ScheduleBatch → ModelWorkerBatch → ForwardBatch 三段表示
② 单元之间只认服务名单元通过服务名找对方，不 import 对方的对象。这样重载一个单元时，依赖它的单元能被找出来一起重载，不会留着旧对象。Cordis 的 Context / Service / inject
③ 调度 = 调度逻辑 + 插槽里的策略 + 状态单元请求表和账本是状态单元；调度逻辑在固定位置调用决策点，策略只拿快照、只返回决定，由调度逻辑校验和执行。mini-sglang 的 PrefillManager / DecodeManager 拆法；sglang 的 schedule_policy
④ 模型 = 层单元的组合；层只认 definition层调用的是“算什么”（definition），具体用哪个 kernel（solution）在编 plan 时定下来。mini-sglang 的 BaseOP；sglang 的 KernelSpec、BaseFusedOp
⑤ 一种状态 = 一个存储单元 + 一个记账插件每层声明要存什么；worker 里的存储单元管显存和快照，调度宿主里的记账插件按同一份声明记账。sglang mem_cache/kv/decl.py（lifetime × geometry）；mini-sglang 的 kvcache 接口
⑥ MoE 是五段流水线，每段可单独换路由 → 查放置表 → dispatch → 专家计算 → combine。段与段之间靠约定好的数据格式对接。sglang token_dispatcher/base.py、moe_runner/base.py
⑦ graph 只能由 plan 单元录录的时候把派生边登记给 core.deps，replay 前检查。sglang BaseCudaGraphBackend
⑧ 所有改动都走 core.changeagent 的 apply、启动、配置、EPLB 重排，都是 change-set：推导动作 → epoch 边界停下 → 执行 → 提交或撤回。Cordis 的 HMR 回滚；v0-plan 4.7

另有一条硬约束：依赖只有一个方向，RSI 平面 → 引擎。引擎不 import 任何 rsi.*，拆掉 RSI 平面后引擎照样能服务、能 apply。

5. 图上所有的边

设定：v0 只支持 Qwen3.8-27B，有 TP；没有 EP、EPLB、DP attention、压缩 KV、跨层共享、量化权重、mHC、Engram。某天 DS 1017 发布了，agent 要在这个 v0 上一步步把它支持起来。每一步都是一次（或几次）apply，问的是：每一步改了什么、框架做了什么、是不是在包络内。
已决定：v0 就只含 Qwen；v0.1 才含 DS 1017，就按这张表的路线从 v0 演进出来。

“包络”的五种结果： 包络内 只新增或替换单元，接口不变； 已有动作 用框架已有的动作（起新实例、重建 rank 进程）； 退路 要重启进程或引擎（native 库、平台升级）； 扩展接口 要改单元之间的接口，接口两边的单元在同一个 epoch 一起重载； 包络外 要改框架本体。

结论

    实验中发现的设计问题，以及改成了什么

    只能重启的情况（Python 进程的本质限制，Cordis 也一样）

    • native 扩展（.so、pybind、CUDA C++）装进进程后卸不掉 → 重启用到它的 rank 进程。
    • torch / CUDA / 驱动升级 → 平台变化，重启引擎。
    • 只能每进程初始化一次的库（NVSHMEM）第一次接入 → 重启 rank 进程。
    • 框架本体的代码改了 → 重启引擎。
    对 v0.1 的启发：v0.1（DS 1017）就按这 16 步来做，每一步都 apply 到正在跑的引擎上。这样 v0.1 本身就是通用性验收：如果哪一步不得不改框架本体，就说明接口还不够通用，记进包络失效日志。
    设定：v0.1 在一台 8 卡机器上跑 DS 1017（DP8 + EP8），所有进程都在这台机器上。v0.2 要跑两台机器、16 张卡（DP16 + EP16）。agent 照样一步步 apply，问的还是：每一步改了什么、框架做了什么、是不是在包络内。

    结论

      实验中发现的设计问题，以及改成了什么

      v0 不用第二台机器也能测 P7：在一台机器上起两个节点代理，假装成两台主机（主机 id 不同、强制走 TCP、各自一个快照目录），用假执行器把变更路径都跑一遍（启动、apply、两阶段提交、回滚、拓扑变化、“一台主机掉了”）。这样 CI 里就能守住 P7。
