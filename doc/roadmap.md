# 路线图

- 日期：2026-11-05
- 真源说明：设计以 [modules.html](modules.html) 为准（发起人已通读并认可）；本文只规定**做的顺序和每一步的验收**。v0-plan.md 第 9 节的里程碑按本文调整。
- 每个阶段的详细规格放在 [specs/](specs/) 下，一个规格一个文件，不写进本文。

## 总体思路

1. **先做一个可验证的骨架，再大规模迁移。** 骨架定下来以后，sglang 的每个组件都能对应成“一个单元 + 一组契约测试”，可以很多人、很多 agent 并行搬。没有骨架就开始搬，搬过来的东西各有各的写法，最后要返工。
2. **骨架不闭门造。** 和骨架并行做一个用完就扔的 GPU 探针，尽早让契约碰到真硬件。
3. **“完备”要能执行。** 每个阶段的验收都是能跑的测试，不是文档。

## 阶段

### 阶段 0：纸面规格

- 内容：
  - 单元清单的格式；单元的编写接口。
  - 七条原则落成具体的数据结构：mesh、开放记录、状态声明、能力声明、change-set、拓扑数据。
  - 框架本体七个组件的规格（[specs/](specs/)）。
  - 用 DS 1017 和 LoRA 做纸面包络测试：它们的每种状态和算子能不能用这些接口表达，表达不了的写进包络失效日志。
  - SM100 环境核查清单。
- 验收：规格评审通过；纸面包络测试有结论；骨架的接口签名写成 Python 存根，能通过类型检查。

### 阶段 1：可验证的骨架（第一个完整交付）

- 内容：
  - 框架本体七个组件：单元运行时、配置与运行环境、进程间传输（共享内存和 TCP）、平台（只有 fake）、节点代理、进程管家、变更事务。
  - 控制面单元：系统身份、清单与静态检查、影响分析（含 dry-run）、控制接口。
  - 一套**玩具领域单元**，写法和真单元一样，但不含模型语义：玩具调度逻辑、玩具策略、玩具请求表和账本、玩具 worker 循环、玩具状态单元、玩具 plan。
  - fake 平台提供一个**假 CUDA graph**：录的时候记下按地址、按值的依赖；依赖变了却没有重录就去 replay，直接报错。这样“绑定方式”这套逻辑在 CPU 上就能测。
  - CI。
- 验收（三类测试全部通过，不碰 GPU，不碰真模型）：
  1. **场景测试**：modules.html 全景图里的 9 个场景，全部变成用假执行器跑的测试。
  2. **不变量测试**（随机测试加故障注入）：
     - 任何单元重载前后，注册表一致，没有残留；
     - 提供者重载时，依赖它的单元一定跟着重载；
     - 卸载顺序总是先卸使用方、再卸持有方；
     - 两阶段提交是原子的：任一参与者失败，全部撤回，身份不变，服务继续；
     - 一步之内只用一个版本；
     - dry-run 给出的计划和实际执行的完全一致；
     - 同一个起点加同一个 change-set，算出的身份总是一样；
     - 一台机器上起两个节点代理模拟两台主机时，以上全部成立（P7）。
  3. **覆盖检查**：每一种边、动作阶梯的每一级、三类模块（逻辑单元、状态单元、框架本体），都至少被一个测试走到。
  - 另外：拆除检查（不装 `rsi/` 也能构建、服务、`apply`）。

### 阶段 1′：GPU 探针（和阶段 1 并行，用完就扔）

- 只回答三个问题：
  1. 在 SM100 上，把一个小模型单元卸掉、重新 import、装上以后，decode CUDA graph 能正确重录、正确 replay 吗？
  2. 按规定的卸载顺序，会不会出现 graph 读到已释放显存？
  3. 同一个 Python 进程里反复重载后，会不会有撤不掉的残留（`torch.library` 注册、CUDA stream、显存池碎片）？
- 另外从 sglang 搬一两个组件当“契约探针”：attention backend 的接口、paged KV 的状态声明，看单元接口和状态声明装不装得下。
- 产出：一份结论报告；发现的问题反馈到阶段 0、阶段 1 的契约里。探针代码不进骨架。

### 阶段 2：迁移 Qwen3.8-27B

- 内容：按单元从 sglang、vLLM 搬过来，每个单元都带 PyTorch 参照实现和契约测试，可以大规模并行。包括：层、attention（full attention 和 GDN）、状态种类（paged KV、GDN recurrent / conv state）、权重存储、真实执行后端、cuda_sm100 平台、真 CUDA graph、调度逻辑和默认策略、固定长度投机、前缀复用、OpenAI 前端。
- 验收：v0-plan 原来的 M2：全模型和 HF 参照在容差内对齐；快速测试层里“批量对单条”“前缀命中对不命中”“开投机对不开”“decode graph 对 eager”“开重叠对不开”五组对比完全一致（最后一组 2026-11-07 加，见 [specs/stage2-contract.md](specs/stage2-contract.md) §4.4）；能服务流式请求。
- 单元清单、接口、分工和里程碑：[specs/stage2-contract.md](specs/stage2-contract.md)。
- 进度（2026-11-13）：M2a、M2b、M2c 完成，M2d 进行中；各里程碑按实际做的改过描述，见 [specs/stage2-contract.md](specs/stage2-contract.md) §1.3。前缀复用照 SGLang 搬，做完了（#59，[specs/prefix-cache.md](specs/prefix-cache.md)）；M2d 还剩 MTP 投机和多 rank 配置。

### 阶段 3：在真 GPU 上跑全变更机制

- 内容：阶段 1 的机制换成真 GPU 上的真单元：refit、grow、后台重录 graph、按需排空、跨 rank 两阶段提交、改并行配置。
- 验收：在 TP1 和多 rank 配置上，v0-plan 第 7 节的 P2–P10、P18–P24 通过。

### 阶段 4：评测服务、谱系与发布

- 验收：P11–P17 通过。

### 阶段 5：通用性验证

- 内容：跑完 v0-plan 第 8 节的全部植入缺陷；三种完全不同的脚本化 RSI 循环（策略搜索、换 kernel、自由修改引擎代码），只用公开接口；一次真实 LLM agent 的冒烟；面向 agent 的使用文档。
- 验收：每个缺陷都被发现或写进包络失效日志；三种循环都跑通，框架里没有为任何一种写特例。**到这里 v0 完成。**
