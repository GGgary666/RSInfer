# 在一个一直跑着的引擎上接手 KV 写入和槽列表的 kernel（2026-11-11，RTX 4090 D）

记录人：Claude Fable 5.2（Claude Code）。对应的工作是分支 `exp/sm100-kv-store-indices`，结果在 [../evaluations/real-kernels-kv-store-indices.md](../evaluations/real-kernels-kv-store-indices.md)。

Gemini 写了一半的两个 kernel，我接手。用户的要求是："你一会要是再改引擎的话热改就行了，尽量试试怎么样。"这份记录写的是照着做下来怎么样。上一份记录（[2026-11-11-real-kernels-hot-apply.md](2026-11-11-real-kernels-hot-apply.md)）里我大半是冷启动的；这一次引擎侧的改动全部是 apply 上去的。

## 结论

1. **引擎从头到尾只起了一次。** 从上一批的树冷启动，之后 13 次 apply 提交、1 次撤回、3 次 dry-run，都在这一个引擎上。
2. **排查和验证都在引擎里做，几秒钟一个答案。** launch 数、两个新 kernel 在真实请求上对不对，都是临时写一段检查、apply、读日志得到的。
3. **"热改时新增一个加载时要编译一分钟的单元"没问题**：编译发生在准备阶段，引擎不暂停。
4. **"改这个单元的 C++ 源码再热改"第一次会失败**：重载在暂停期内，编译超过执行时限，变更撤回，引擎有 54 秒只回 503。先在引擎外编译再 apply 就是两三秒。我给单元加了预编译入口和提示，写进了 skill。
5. **正式的 GPU 测试仍然要停掉引擎才能跑**（一张卡放不下），而且它抓到了引擎里的检查抓不到的东西：一个写错的测试。

## 好用的地方

- **计划每次都对**：改哪个文件，重载的就是那个单元和依赖它的 `core.plan`；新增的单元单独列在准备阶段。dry-run 和实际执行一致。
- **新增一个要编译的单元不打断服务。** 我原来担心这 55 秒会卡在暂停期里，实际上协议把"装新单元"放在准备阶段，时限是 `change.prepare_timeout_s`（默认 600 秒）。
- **撤回是干净的**：那次超时以后，引擎的身份、输出都没变，不需要恢复。
- **在引擎里查比在 pytest 里查快，也更像真的**：profiler 那次量到的是带真调度器的一步；对照参照实现那次用的是 8 个并发的真请求，包括 graph 回放的步（`prepare` 在 graph 之外，每步都跑 Python）。

## 别扭的地方

- **改 C++ 源码，第一次 apply 必然失败**，而且失败要花一分钟：协调者 30 秒就判了超时，但 worker 还卡在编译里，撤回要等它编译完。失败的那次顺便把产物编进了缓存，所以"再 apply 一次就成"，这很容易让人摸不着头脑。
  - 现在的办法是约定：改完先跑 `python -m kernels.cuda.ops`。单元在要现编译时会在日志里打一行提示。
  - 更彻底的办法是让单元能在准备阶段做这件事（协议里动作有 `prepare` 钩子，新单元也在准备阶段装），我没有去设计。
- **正式测试还是得停引擎。** GPU 测试一次要搭一两个 worker 栈，和引擎一起放不下 24 GB。所以流程是：引擎上改和查，最后停掉引擎跑一遍 pytest。这次 pytest 抓到的是测试代码自己的错，引擎里的检查看不到它。
- **引擎的源码就是工作目录**，临时检查和要提交的修改混在同一棵树里。我每次加检查前先备份文件，查完恢复，再 `grep -rn PROBE engine` 确认。用单独的 worktree 做临时检查更省心，但那样要提交的修改就得在两处之间搬。

## 没覆盖的

- SM90 以上的 PDL 路径、SM100 上的效果：这台机器跑不了，没有试。
- 这次没有碰到检查代码抛异常的情况（检查都包在 `try/except` 里）。
