# Ascend 910C 部署与 RSI 实测

在 `dev/ascend_a3_gg` 上使用当前机器的 Ascend 910C、CANN 9.2.0、PyTorch 2.10.0 和 `torch_npu` 2.10.0.post7。Qwen3 使用 `/local/models/Qwen3-0.6B` 的 BF16 权重。GLM 参考配置为本机 `glm_53_flash_opt` 中的 DP2 × TP8、EP、5-token MTP 和 MemCache。部署命令见 [deploy/README.md](../../deploy/README.md#ascend-910c)。

## Qwen3-0.6B

单 die、128 token KV 页、4096 上下文窗口、512 token prefill 调度预算。每轮取 16 个长度为 512 token 的固定提示词，四并发流式生成 64 token。每轮只暖机一次，变更后从空前缀缓存开始。下表取三轮中位数，延迟列分别列出各轮均值和 P90 的中位数。

| 方案 | 输出 tok/s | TTFT 均值 / P90（ms） | TPOT 均值 / P90（ms） | 输出一致性 | 处理 |
| --- | ---: | ---: | ---: | --- | --- |
| CANN 分页 attention 基线 | 90.905 | 111.157 / 170.365 | 42.927 / 44.309 | 48/48 | 基线 |
| CANN 融合 RoPE | 122.714 | 87.931 / 137.404 | 31.670 / 32.555 | 16/48 | 回退 |
| 同一步复用 RoPE 查表结果 | 113.692 | 97.291 / 151.111 | 34.188 / 36.235 | 48/48 | 保留 |

保留方案提高约 25.1% 输出吞吐，TTFT 均值降低 12.5%，TPOT 均值降低 20.4%。融合 RoPE 的随机张量核对在 BF16 容差内，模型级固定请求比较观察到生成序列变化。ATB 的 `_npu_paged_attention` 在当前 ND KV 布局的预检中未通过 setup，继续使用 `npu_fused_infer_attention_score`。

用 `apply` 在同一 worker 上装入 KV-only 前缀缓存和两个 RoPE 方案。保留版本的事务总阶段约 5.20 秒，暂停和执行约 92 毫秒。首次冷启动到控制面提交用 20.06 秒，当时同时运行了 CPU 基线和测试。提交一个无效的 decode 后端会进入 `aborted`，进程列表无重启，回滚后仍能生成与 CPU 参考相同的 12 个贪心 token。CPU 单测以 Hugging Face Qwen3 对比分段 prefill、GQA 和 decode logits。

在两个 die 上以 DP2 再验证一次，四条并发请求全部完成，最长提示词为 1,963 token。两次固定种子的 top-k/top-p 采样输出一致。`sleep` 和 `wake` 都提交成功，唤醒后四条贪心请求和两条采样请求逐字一致。

参考了 vLLM Ascend 的分页物理布局与 CANN 调用，并沿用 RSInfer 的 SGLang 风格模型和前缀缓存边界。 [vLLM Ascend attention](https://github.com/vllm-project/vllm-ascend/tree/main/vllm_ascend/attention) · [SGLang Qwen3](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/models/qwen3.py)

## GLM-5.3-Flash 与 MemCache

使用 `/local/models/GLM-5.3-Flash-w8a8`、vLLM 0.30.0 和 vLLM Ascend 0.30.0rc2。由 `glm53` 管理 16 个 Ascend die 上的推理进程，复用本机参考 hooks、MTP 和 ACL Graph 配置。`AscendStoreConnector` 的客户端使用 0 DRAM 配置，MetaService 与独立池提供 256 GiB DRAM。参考仓库脚本生成每组 16 条请求，四并发流式生成 128 token。16K 组使用独立前缀，60K 组先暖一个 55,296 token 的共享前缀。各轮在独立评测目录生成前缀和缓存盐。

| 方案 | 组 | 输出 tok/s | TTFT 均值 / P90（ms） | TPOT 均值 / P90（ms） |
| --- | --- | ---: | ---: | ---: |
| 参考 `exp_final_champion_warm` | 16K | 72.15 | 2351.0 / 3191.6 | 36.0 / 48.8 |
| 参考 `exp_final_champion_warm` | 60K | 110.30 | 1538.3 / 2320.8 | 23.1 / 28.3 |
| RSInfer 部署，8192 × 64 | 16K | 70.03 | 2572.3 / 3617.5 | 35.6 / 46.5 |
| RSInfer 部署，8192 × 64 | 60K | 108.50 | 1480.6 / 2278.6 | 24.3 / 30.2 |
| RSInfer 部署，8192 × 32 | 16K | 79.94 | 2588.3 / 3278.4 | 29.4 / 34.4 |
| RSInfer 部署，8192 × 32 | 60K | 110.33 | 1348.3 / 2325.5 | 23.4 / 27.4 |

首次启动的池初始化耗时 22.275 秒，vLLM API 就绪耗时 192.034 秒，首条推理额外耗时 0.646 秒。两组各有 16 条成功请求，6 项精度与长上下文 needle 检查通过。60K 组覆盖了 86.23% 的缓存 token。MemCache GET 命中 368/368，分配失败计数保持为 0。

用 `restart --max-seqs 32` 将 ACL Graph 最大桶从 384 降为 192。原进程退出后池继续运行，健康检查和复用耗时 0.010 秒。新 vLLM API 就绪耗时 189.046 秒，重启命令到首条推理结束共 193.314 秒。重启前用独立缓存盐提交一条 9,490 token 的请求，首次缓存命中为 0。新推理 PID 上重放该请求，从原池恢复 8,064 token，MemCache GET 命中 80/80。

保留 32 序列作为默认值。与本次 64 序列基线相比，16K 输出吞吐提高 14.1%，TPOT 均值降低 17.4%，TTFT 均值增加 0.6%，P90 降低 9.4%。60K 输出吞吐提高 1.7%，TPOT 均值降低 3.7%，TTFT 均值降低 8.9%，P90 增加 2.1%。两组共 32 条请求全部成功，6 项精度检查通过，其中 4 项输出与基线完全一致。对比使用各一轮四并发负载，`--max-seqs 64` 可恢复原并发序列上限。

本节的 GLM 数据来自 vLLM Ascend 对照。RSInfer 原生 GLM 路径已接入 W8A8 MoE、KDA、稀疏 attention、MTP 和 MemCache 状态恢复。原生优化及与同一评测对照的数据见 [GLM-5.3-Flash 原生执行优化记录](2026-11-26-glm53-native.md)。
