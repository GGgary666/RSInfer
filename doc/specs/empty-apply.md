# 变更只作用于空引擎

- 日期：2026-11-09
- 状态：已实现（本 PR）。由 @wutianyuan1 决定，@gaow0007 已知道。
- 取代：和下面"取代的旧规则"冲突的地方，一律以本文为准。

## 1. 为什么

RSI 改引擎的节奏本来就是"测 → 改 → 测"，改的时候上面有没有请求在跑，由 RSI 自己的流程决定。

另一方面，有请求在跑时做变更，在途请求"该怎么办"是静态分析不出来的：
- 框架分不出一次改动有没有改变计算结果。比如改了 kernel 或模型代码，在途请求已有的 KV / GDN 状态是旧代码算出来的，新代码会直接接着用。
- 改状态单元的代码（或它 import 的共享模块）会把它重建成空的。持久 batch 还在，下一步照常跑，读到的却是空状态，采出错的 token，不报错。

所以规定：apply 时引擎必须是空的。

## 2. 规则

1. **只改 live 配置键**（比如 `sched.overlap`）：照旧直接生效，不管引擎空不空。只算 `binding = "live"` 的键；带 hook 的 `plan` 绑定键也要排空。
2. **其他所有变更**，apply 时引擎必须是空的。包括：
   - 代码、清单、startup 配置、拓扑；
   - 状态动作（比如 `refit`）；
   - 控制面单元。
3. **默认（不带参数）**：引擎不空就拒绝。什么都不改，返回的诊断写明：
   - 前端有几个打开着的请求；
   - 调度器有几个在跑、几个在排队的请求，以及几个在途的步；
   - 两条可以接着用的命令。

   不做成交互式的，由调用方（RSI agent）看了提示自己决定。
4. **`apply --wait-empty [SECONDS]`**：
   - 关门：新请求回 503 加 `Retry-After`；
   - 已经进来的请求照常跑完，空了就 apply，然后开门；
   - 默认最多等 3600 秒。到了还没空，变更失败，什么请求都不中止，照常开门。
5. **`apply --force`**：
   - 立刻结束所有请求：`finish_reason` 是 `abort`，错误信息是 "ended: the engine is being changed (apply --force)"（共享常量 `core.contracts.requests.ENDED_BY_CHANGE`）。HTTP 客户端收到 503 和 `Retry-After`（流式请求在错误帧里收到 503），和关门时一样，表示稍后重试；前端按错误本身判断，不看自己的门这时关没关；
   - 等在途的步结束（最多 10 秒），再 apply。
   - worker 出错以后，不会再有新的步，占着行的请求自己永远结束不了：这时拒绝和等待两种模式都直接失败，提示只能用 `--force`。等待开始以后才出错的，也在下一次检查时失败，不等满上限。
   - 2026-11-11 起不再这样：worker 出错时调度器就结束引擎里的全部请求，引擎是空的，三种模式都直接排空；变更提交以后调度器重新开始服务（`doc/framework-bugs/2026-11-11-a-repaired-worker-stays-stopped.md`）。
6. **门在前端**（`frontend.http`）。
   - 前端先关门，再数打开着的请求：一个请求要么被数到，要么看到门已经关了。
   - 调度器排在前端后面时照常读流：前端关门之前已经放进来、还在路上的请求，等待模式下照常跑完，强制模式下被拒掉；前端要等它们都结束才算排空。
   - 没有前端的引擎（测试）由调度器当门（规划器给它的排空参数 `gate` 为真）：引擎空了以后，它不再从流里读新请求，直到变更提交或撤回。新请求留在流里，用变更以后的代码跑。
   - 变更重载了前端时，新实例是在暂停期内建出来的，它一直关门，直到进程恢复（变更提交或撤回之后）：它的 HTTP 线程不受暂停影响，否则会提前接请求。
   - 变更提交以后，调度器要先收到每个 rank 在新身份下报来的 `Capacity`，才开始规划：这次变更可能把存储重建得更小，而旧身份下发出的记录可能还在路上。worker 一换身份，下一步就报一次。变更没定下来之前（执行阶段），worker 不报容量：撤回时存储按原来的大小重建，账本也一直是原来的值。
7. **"空"指**：
   - 前端没有打开着的请求，包括已经过了门、还没登记进来的那一个；
   - 调度器的请求表里没有没结束的请求；
   - 没有在途的步。worker 已经出错时，它那些永远回不来的步不算。
8. **以后的 prefix cache**：每次非 live 的变更都整个清掉。现在还没有 prefix cache。
9. **不做状态迁移**（导出 / 导入）：引擎空了，重建状态单元不丢东西。唯一的例外是权重：
   - 改 `core.state.weights` 的代码，会在暂停期内从 checkpoint 重新读一遍，27B 要几分钟；
   - 用 `refit` 换过的权重会回到 checkpoint 里的值。

   先接受这个代价，以后需要时再单独处理。

## 3. 实现（2026-11-09）

**框架本体**（改动尽量小）：
- `ChangeMeta.when_busy`（`refuse` / `wait` / `force`）和 `ChangeMeta.wait_s`：把调用方的选择带给持有请求的单元，框架自己不碰请求。
- 排空动作也会收到 `commit()` / `abort()`，补上了 `state-changes.md` §5.2 记下的缺口：
  - `start_drain` 抛了异常也照样会收到；
  - 收到它的是当时在服务的那个实例。
- `core.control.client`：
  - `apply` 增加 `--wait-empty [SECONDS]` 和 `--force` 两个参数；
  - `apply` 默认打印结果的摘要：状态、身份、notes、每个进程动了什么、各运行时实际做了什么、诊断；
  - `--json` 打印完整结果。原来的完整结果带着每个进程变更后的整份计划（所有清单和配置值），改一个键就有上千行。
- 吸收了 #39：要求重启引擎时，诊断写明计划给出的原因。
- 排空检查出错时（比如等待到期），参与者退出排空状态，不会在每个安全点再问一遍（#42 评审）。
- `proc.control@1` 多了只读属性 `paused`：进程在暂停中。前端的 HTTP 线程不受暂停影响，靠它判断自己是不是在变更的执行阶段建出来的。
- 共享契约 `Capacity` 多了可选字段 `identity`：发送时 worker 服务的身份，默认 `""`，在途的旧记录照样能读。

**单元**：
- `core.deps`：除了只改 live 键的变更，其余变更都给每个原地参与、且在运行的、声明了 `drain` 动作的单元加一个 `drain`，参数是这次变更的模式。等待上限：
  - `wait`：取 `wait_s`；
  - `force`：10 秒；
  - `refuse`：用框架的默认值。

  #35 加的"会重建在途状态的配置变更要求重启引擎"去掉了：引擎空了，状态单元直接原地重建。
- `frontend.http`：门（`api.py` 的 `Gate`）。在暂停期内建出来的实例，一直关门到进程恢复。
- `core.sched`：`drain.py`。
  - `refuse`：有请求或在途步就失败；
  - `wait`：把里面的跑完；
  - `force`：结束所有请求，在关门期间到达的请求一律拒绝，只等在途的步。

  只有它是门时（`gate`），空了以后才停止收新请求。变更提交以后，在收到每个 rank 新身份下的 `Capacity` 之前，不规划任何一步。
- `core.worker`：进程身份变了（或新实例第一次走），下一步就报一次 `Capacity`，带上当时服务的身份。新实例不在执行阶段一建好就报：那时的存储还是候选，变更可能撤回（#42 复审）。
- `core.state.alloc`：池子在什么都没持有时允许缩小。存储换了 dtype 或预算重建以后，报上来的容量可能变小。

**测试**：
- `tests/units/core/test_deps.py`：排空动作、只改 live 键时的例外；
- `tests/units/executors/test_config.py`：状态配置变了会原地重载存储；在空的 worker 上就地重建以后，生成的 token 和一开始就用新值启动的 worker 相同；
- `tests/units/scheduler/test_drain.py`、`tests/units/frontend/test_gate.py`；
- `tests/framework/change/test_transactions.py`：排空收到 `commit` / `abort`，拒绝时变更失败并带上原因；
- `tests/units/scheduler/test_processes.py`：经真实控制面拒绝、等待、强制；
- #42 评审补的测试：前端后面的调度器照常处理晚到的请求；变更后在新身份的 `Capacity` 到齐之前不规划；worker 换身份后重报 `Capacity`；暂停期内建出来的前端关门；排空到期只问一次；
- `tests/scenarios/test_m2a.py`：整个引擎加命令行客户端，依次是拒绝、`--force`、普通 apply、`--wait-empty`。

## 4. 取代的旧规则

- **`modules.html`**：
  - 动作阶梯下面那句"只有会影响在途请求的动作才排空，而且只排空受影响的那部分请求"：现在除了 live 键，每次变更都把引擎整个排空；
  - 状态单元那条"提供迁移函数的可以不排空"：现在不做迁移。
- **`state-changes.md` §3–§6**（按 `drain_on_reload` 判断、只排受影响的请求、版本迁移）：作废。
  - 清单里的 `[state] drain_on_reload` 和 `migrate` 字段还留着，但已经没有代码读它们；
  - §5.1 "参数只给事实"那套参数，换成了这次变更的模式。
- **`change.md` §7 第 5 条**（"不影响在途请求的改动不排空"）：现在只有只改 live 键的变更不排空。
- **`stage2-contract.md`**：
  - §5.5.5：迁移表，以及 #35 的"要求重启引擎"，都改为排空后原地重建；
  - §8.6、§9.4 里"边服务 A 边准备 B"：分片重录、候选和当前隔离、新旧 graph 并存，都不需要了。graph 在暂停期内、引擎为空时重录。
- **`deploy/README.md`** 里"请求生成到一半时 apply"的那组热改：现在默认会被拒。
- **场景 8**（`tests/scenarios/test_scenarios.py`）：不再声称"在途请求接着跑"。它的玩具请求表没有声明 `drain`，测的是请求表不被重载。

**不受影响的**：
- 暂停协议；
- worker 故障的处理：那不是变更；
- `Resync` / 全量增量；
- 重叠一步时的延迟释放；
- 空闲时补发 `Capacity`；
- kernel 目录 `version` 变了以后重新解析。

## 5. 已知的边界

- 只有原地参与变更的进程会排空。如果前端或调度器所在的进程这次要重启（拓扑或原生扩展变了），它就不参与排空，只能靠另一边：前端要重启时，调度器那边仍然会检查引擎空不空。
- `--force` 结束了几个请求，现在只打在调度器的日志里，没有进 `ChangeResult.drain_outcomes`：框架只在等待到期时才收集这一项。
- 一次变更在等待引擎变空时，后来的变更在队列里排着。
- 只做状态动作的变更（比如 `refit`）提交后身份不变，worker 不会因为换身份重报 `Capacity`。调度器要等它下一次空闲补报（`worker.announce_every_s`，1 秒）才恢复规划。这类变更不改存储的大小。
