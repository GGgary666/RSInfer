# 规格：进程间传输 `core.ipc`

- 类型：框架本体。每个进程里有收发接口；进程之间是通道。改了它要重启引擎。
- 借鉴：mini-sglang `message/`、`utils/mp.py`。
- 公共约定见 [README.md](README.md)。

## 1. 职责

1. 三种通道：请求 / 回复（RPC）、发布 / 订阅、每步记录流。
2. 按两端位置自动选后端：同一台机器走共享内存，跨机走 TCP（ZMQ）；以后可加 RDMA。
3. 地址来自拓扑数据，不写死 `localhost`、不用本机 PID。
4. 只管“怎么传”。记录里有什么由各单元自己定义（带版本的 msgspec 结构）。

## 2. 通道

| 通道 | 用途 | 语义 |
|---|---|---|
| RPC | 变更事务、控制命令、进程报到 | 请求 / 回复；带超时；幂等由调用方保证 |
| 发布 / 订阅 | 事件流、心跳 | 至多一次；订阅者可以丢消息 |
| 每步记录流 | StepPlan、StepResult | 有序、不丢、单生产者；背压：消费者跟不上时生产者阻塞 |

- 每步记录流的同机后端：节点代理分配的共享内存环形缓冲区。跨机后端：ZMQ over TCP。两者对单元暴露同一个接口。
- 通道的端点按 `Endpoint = (ProcId, channel_name)` 寻址。

## 3. 开放记录

- StepPlan、StepResult 这类记录由多个单元各自贡献分段（P2）：
  ```python
  class OpenRecord(msgspec.Struct):
      schema: str                 # 例如 "sched.step_plan@1"
      epoch: int
      sections: dict[str, bytes]  # 分段名（例如 "attn.metadata@1"）-> 编码后的分段
  ```
- 收方只解码自己认识的分段；缺了必须的分段报错，多出来的分段忽略。
- 按 rank 索引的记录（P3）：每个 rank 一份；TP 时各份内容相同。

## 4. 故障

- 对端失联：RPC 超时返回 `Failed`；每步记录流报告“对端丢失”，由调用方上报给控制面。
- 版本不对：拒收并报诊断（见 README 的消息信封）。
- **控制消息必须幂等**：一个 RPC 超时以后，它的请求可能还在发送队列里，等对端恢复后才送到（迟到的请求）；同一个请求也可能被重试。所以所有经过 RPC 的控制消息，收方都必须能安全地处理重复和迟到的消息，例如按 change id 去重。

## 5. 验收测试（阶段 1）

1. 同一份单元代码，同机走共享内存、跨“假主机”走 TCP，行为一致。
2. 每步记录流有序、不丢；消费者变慢时生产者被阻塞，不会丢数据。
3. 开放记录：新增一个分段不影响老的收方；缺必须分段时报错。
4. 对端被杀后，RPC 在超时内返回 `Failed`，每步记录流报告对端丢失。
5. 全部代码里找不到 `localhost` 和本机 PID 作为地址。
