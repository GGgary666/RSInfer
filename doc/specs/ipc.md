# 规格：进程间传输 `core.ipc`

- 类型：框架本体。每个进程里有收发接口；进程之间是通道。改了它要重启引擎。
- 借鉴：mini-sglang `message/`、`utils/mp.py`。
- 公共约定见 [README.md](README.md)。

## 1. 职责

1. 三种通道：请求 / 回复（RPC）、发布 / 订阅、每步记录流。
2. 按两端位置自动选后端：同一台机器走共享内存，跨机走 TCP（ZMQ）；以后可加 RDMA。
3. 地址来自拓扑数据，不写死 `localhost`、不用本机 PID。
4. 只管“怎么传”。记录里有什么由各单元自己定义（带版本的 msgspec 结构）。

## 2. 通道

| 通道 | 用途 | 语义 |
|---|---|---|
| RPC | 变更事务、控制命令、进程报到 | 请求 / 回复；带超时；幂等由调用方保证 |
| 发布 / 订阅 | 事件流、心跳 | 至多一次；订阅者可以丢消息 |
| 每步记录流 | StepPlan、StepResult | 有序、不丢、单生产者；背压：消费者跟不上时生产者阻塞 |

- 每步记录流的同机后端：节点代理分配的共享内存环形缓冲区。跨机后端：ZMQ over TCP。两者对单元暴露同一个接口。
- 通道的端点按 `Endpoint = (ProcId, channel_name)` 寻址。

## 3. 开放记录

- StepPlan、StepResult 这类记录由多个单元各自贡献分段（P2）：
  ```python
  class OpenRecord(msgspec.Struct):
      schema: str                 # 例如 "sched.step_plan@1"
      epoch: int
      sections: dict[str, bytes]  # 分段名（例如 "attn.metadata@1"）-> 编码后的分段
  ```
- 收方只解码自己认识的分段；缺了必须的分段报错，多出来的分段忽略。
- 按 rank 索引的记录（P3）：每个 rank 一份；TP 时各份内容相同。

## 4. 故障

- 对端失联：RPC 超时返回 `Failed`；每步记录流报告“对端丢失”，由调用方上报给控制面。
- 版本不对：拒收并报诊断（见 README 的消息信封）。
- **控制消息必须幂等**：一个 RPC 超时以后，它的请求可能还在发送队列里，等对端恢复后才送到（迟到的请求）；同一个请求也可能被重试。所以所有经过 RPC 的控制消息，收方都必须能安全地处理重复和迟到的消息，例如按 change id 去重。

## 5. 验收测试（阶段 1）

1. 同一份单元代码，同机走共享内存、跨“假主机”走 TCP，行为一致。
2. 每步记录流有序、不丢；消费者变慢时生产者被阻塞，不会丢数据。
3. 开放记录：新增一个分段不影响老的收方；缺必须分段时报错。
4. 对端被杀后，RPC 在超时内返回 `Failed`，每步记录流报告对端丢失。
5. 全部代码里找不到 `localhost` 和本机 PID 作为地址。

## 6. 宿主持有的数据通道 `proc.streams@1`（2026-11-08）

单元之间收发每步记录（调度器 ↔ worker、前端 ↔ 调度器）用这个宿主服务（`core/ipc/channels.py`），不自己建流。原因：
- 单元自己建流，重载一次地址就变了，对端得重新查；
- 同机的共享内存环要由节点代理起名；
- 对端的地址要通过进程管家查。

**接口**。所有调用都在宿主线程上：

```python
channels.reader(name, peer_host) -> ChannelReader  # 宿主持有；同名再要返回同一个，循环单元重载后拿回原来的读端
channels.writer(proc, name)      -> ChannelWriter  # 写到 proc 的读端 name，经进程管家查地址
channels.writer_to(address)      -> ChannelWriter  # 写到记录里交过来的地址（如前端的返回地址），不重新查
channels.discard(address)                          # 这个地址的读端已知不在了

reader.read(timeout) -> bytes | None  # 写端离开不算错，没人写时返回 None
reader.generation                     # 这个读端有过几个写端
writer.write(data, timeout) -> bool   # False：现在没有读端可写（还没登记，或进程刚被换掉），什么都没发；
                                      # 读端在但跟不上，照旧抛 TimeoutError
writer.generation                     # 连上过几次读端
```

**写端可替换**。`open_reader(..., replaceable=True)` 打开的读端，一个写端关闭或死掉，下一个连上来的写端接着写，读端不报 `StreamClosed` / `PeerLost`：
- **TCP**：每帧带写端的随机 id。读端遇到新 id 的第 0 帧就换成这个写端；被换掉的写端迟到的帧直接丢掉，不和新写端的记录交错。
- **共享内存**：环头多了一个写端计数。新写端只在旧写端正常关闭、或者心跳超过 `ipc.peer_timeout_s` 没更新时才能接管，否则 `RingBusy`。所以同一时刻只有一个写端，单生产者的前提不变。旧写端已经发布的记录留在环里，读端先读完；写到一半的记录没有发布（长度和 head 最后写），读端看不见。
- **换写端或换读端时，在途的记录可能丢失**：TCP 上，旧写端还没被读的帧会丢；读端换了，写进旧读端的记录也会丢。两边的 `generation` 变了，就说明发生过一次替换。怎么处理（比如整批重发）由单元决定，通道不替它决定。
- 不加 `replaceable` 的流语义不变：第二个写端报 `PeerLost`，写端关闭报 `StreamClosed`。

**登记和查找**：
- CheckIn 时已有的读端随 CheckIn 登记。之后才打开的读端，宿主发 `proc.publish_endpoint@1` 补登记。
- 别的进程用 `Lookup` 查，只查得到 RUNNING 的进程的地址。
- 写端没有读端可写时才去查，两次查询至少隔 `ipc.lookup_retry_s`（默认 0.1 秒）。连上以后，正常收发时不查。
- 共享内存环的名字：宿主经进程管家把 `AllocShm` 转给本机节点代理；节点代理记下名字，进程退出后删掉这个环。

**顺带修正的流行为**：
- TCP 的 `read(0)` 原来每次空读固定等 10 ms，现在只看一眼；
- TCP 读端看到对端断开时，先读完已经到达的记录，再报 `PeerLost`；
- 共享内存的写端每次写之前先检查读端，读端已经关闭或心跳超时就报 `PeerLost`，不再先把一个没人读的环写满。

**验收测试**：
1. 两种后端：写端 A 写完关闭，写端 B 接着写，读端按顺序收到全部记录，`generation` 是 2。
2. 两种后端：写端 A 被杀以后，写端 B 接管。共享内存上，A 的心跳超时之前 B 拿到 `RingBusy`。
3. TCP：被换掉的写端迟到的记录被丢掉，不和新写端的记录交错。
4. 不可替换的 TCP 读端遇到第二个写端，报 `PeerLost`。
5. `Channels`：读端只登记一次；写端在读端登记前返回 False，查询有退避；读端所在的进程被换掉后，写端重新查到新读端。
6. 真实进程：进程管家先后重启读端所在的进程和写端所在的进程，数据都能接着流，每个连接内记录不丢、不乱序（`tests/framework/cluster/test_channels.py`）。
7. 真实进程：CheckIn 之后才打开的读端，环名经进程管家向节点代理申请，地址由宿主补登记，写端能查到它。
