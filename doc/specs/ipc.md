# 规格：进程间传输 `core.ipc`

- 类型：框架本体。每个进程里有收发接口；进程之间是通道。改了它要重启引擎。
- 借鉴：mini-sglang `message/`、`utils/mp.py`。
- 公共约定见 [README.md](README.md)。

## 1. 职责

1. 三种通道：请求 / 回复（RPC）、发布 / 订阅、每步记录流。
2. 按两端位置自动选后端：同一台机器走共享内存，跨机走 TCP（ZMQ）；以后可加 RDMA。
3. 地址来自拓扑数据，不写死 `localhost`、不用本机 PID。
4. 只管“怎么传”。记录里有什么由各单元自己定义（带版本的 msgspec 结构）。

## 2. 通道

| 通道 | 用途 | 语义 |
|---|---|---|
| RPC | 变更事务、控制命令、进程报到 | 请求 / 回复；带超时；幂等由调用方保证 |
| 发布 / 订阅 | 事件流、心跳 | 至多一次；订阅者可以丢消息 |
| 每步记录流 | StepPlan、StepResult | 有序、不丢、单生产者；背压：消费者跟不上时生产者阻塞 |

- 每步记录流的同机后端：节点代理分配的共享内存环形缓冲区。跨机后端：ZMQ over TCP。两者对单元暴露同一个接口。
- 通道的端点按 `Endpoint = (ProcId, channel_name)` 寻址。

## 3. 开放记录

- StepPlan、StepResult 这类记录由多个单元各自贡献分段（P2）：
  ```python
  class OpenRecord(msgspec.Struct):
      schema: str                 # 例如 "sched.step_plan@1"
      epoch: int
      sections: dict[str, bytes]  # 分段名（例如 "attn.metadata@1"）-> 编码后的分段
  ```
- 收方只解码自己认识的分段；缺了必须的分段报错，多出来的分段忽略。
- 按 rank 索引的记录（P3）：每个 rank 一份；TP 时各份内容相同。

## 4. 故障

- 对端失联：RPC 超时返回 `Failed`；每步记录流报告“对端丢失”，由调用方上报给控制面。
- 版本不对：拒收并报诊断（见 README 的消息信封）。
- **控制消息必须幂等**：一个 RPC 超时以后，它的请求可能还在发送队列里，等对端恢复后才送到（迟到的请求）；同一个请求也可能被重试。所以所有经过 RPC 的控制消息，收方都必须能安全地处理重复和迟到的消息，例如按 change id 去重。

## 5. 验收测试（阶段 1）

1. 同一份单元代码，同机走共享内存、跨“假主机”走 TCP，行为一致。
2. 每步记录流有序、不丢；消费者变慢时生产者被阻塞，不会丢数据。
3. 开放记录：新增一个分段不影响老的收方；缺必须分段时报错。
4. 对端被杀后，RPC 在超时内返回 `Failed`，每步记录流报告对端丢失。
5. 全部代码里找不到 `localhost` 和本机 PID 作为地址。

## 6. 宿主持有的数据通道 `proc.streams@1`（2026-11-08）

单元之间收发每步记录（调度器 ↔ worker、前端 ↔ 调度器）用这个宿主服务（`core/ipc/channels.py`），不自己建流。原因：
- 单元自己建流，重载一次地址就变了，对端得重新查；
- 同机的共享内存环要由节点代理起名；
- 对端的地址要通过进程管家查。

**接口**。所有调用都在宿主线程上。单元可以把一个读端交给自己的某一个线程，之后只由那个线程使用（前端的 I/O 线程就是这样）：

```python
channels.reader(name, peer_host) -> ChannelReader  # 宿主持有；同名再要返回同一个，循环单元重载后拿回原来的读端
channels.writer(proc, name)      -> ChannelWriter  # 写到 proc 的读端 name，经进程管家查地址
channels.writer_to(address)      -> ChannelWriter  # 写到记录里交过来的地址（如前端的返回地址），不重新查
channels.discard(address)                          # 这个地址的读端已知不在了

reader.read(timeout) -> bytes | None  # 写端离开不算错，没人写时返回 None
reader.generation                     # 刚读出的那条记录是第几个写端写的
writer.write(data, timeout) -> bool   # False：现在没有读端可写（还没登记、进程刚被换掉、TCP 连接还没建好），
                                      # 什么都没发；从不等连接。读端在但跟不上，照旧抛 TimeoutError
writer.generation                     # 真正建立过几次连接
```

**写端可替换**。`open_reader(..., replaceable=True)` 打开的读端，一个写端关闭或死掉，下一个写端接着写，读端不报 `StreamClosed` / `PeerLost`。每条记录都知道是第几个写端写的，`generation` 报的是刚读出那条记录的写端。

- **共享内存**：
  - 环头记着当前写端的代数，每条记录也带上写它的写端的代数。
  - **谁是主人**：写端打开环时，对这段共享内存加一把排他文件锁（`flock`），一直持有到关闭；进程不管怎么结束，内核都会释放这把锁。所以新写端只在旧写端关闭、或者旧写端的进程已经结束之后才能接管。旧写端只是停住了（停顿多久都一样，心跳超时也一样），新写端拿到的是 `RingBusy`，不可能在旧写端还能写的时候接管、被它覆盖。
  - **接管**：读端已经关闭或心跳超时，写端打开就报 `PeerLost`；锁被别人持有，报 `RingBusy`。否则新写端接管，代数加 1。
  - **没有这种锁的平台**（共享内存不支持 `flock` 时，例如 macOS）：退回心跳规则，旧写端心跳超过 `ipc.peer_timeout_s` 就可以被接管。被接管的写端每次写之前、发布之前、发心跳之前、关闭之前都先确认自己还是主人，不是就报 `PeerLost`、什么都不动；但它如果停在"确认"和"写"之间、新写端在这期间接管并发布了记录，它恢复后仍会覆盖那条记录。这种平台只用于开发；引擎在 Linux 上运行。
  - 旧写端已经发布的记录留在环里，读端先读完，代数还是旧的；写到一半的记录没有发布（长度和 head 最后写），读端看不见。
- **TCP**：
  - 每帧带写端的启动时间（ns）和一个随机数，读端按这两个数给写端排序：启动更晚的写端替换更早的。同一台机器上本来就有序；跨机器时，要求时钟误差小于一个进程重启需要的时间（秒级）。
  - ZMQ 会在几个连接之间轮流取帧，所以几个写端的帧可能交错到达。读端只认一个当前写端，按顺序读它的帧：
    - 更早的写端发来的帧，一律丢掉，包括它被替换后才到的第一帧；
    - 更晚的写端发来的帧先存着，等当前写端结束了，再换成那个写端。存了多少帧不算数：当前写端的尾巴可能还在队列里。
    - "结束"有两种证据：读到了它的关闭帧；或者调用方在读的期间，队列一遍遍被取空，它都没有再来帧，累计超过 `peer_timeout_s`。调用方两次查看之间隔得比 `peer_timeout_s` 还久（它在忙别的），这段时间不算：那时它的帧可能正排在队列里没被读。按"静默"切换，只在队列取空的那一刻判断。
    - 存着的帧最多 `ipc.stream_hold_bytes`（默认 64 MiB），先检查再存。超过了，说明两个写端在同时写：读端从此不能用，不再存任何东西，之后每次 `read` 都报同一个 `PeerLost`，直到关掉重开。
  - 所以两个写端的记录不会交错，正常关闭的写端最后几条也不会因为下一个写端先到而丢掉，再长的尾巴也一样。被替换的写端自己不会知道，它之后发的帧被读端丢掉。
- **在途的记录可能丢失**：写端被杀时它还没送达的记录会丢；读端换了，写进旧读端的记录也会丢。`generation` 变了，就说明发生过替换。怎么处理（比如整批重发）由单元决定，通道不替它决定。
- 不加 `replaceable` 的流语义不变：第二个写端报 `PeerLost`，写端关闭报 `StreamClosed`。

**`ChannelWriter` 的连接**：
- 从不等连接。TCP 握手还没完成时 `write` 直接返回 False；超过 `peer_timeout_s` 还没连上，就当这个地址的读端不在了。
- 读端不在的地址记下来，最多每 `peer_timeout_s` 再试一次，不会在一个死地址上反复连、反复加 `generation`；目录给出新地址就马上去连。
- `generation` 只在连接真正建立时加 1：共享内存在接管成功时，TCP 在握手完成时。

**登记和查找**：
- CheckIn 时已有的读端随 CheckIn 登记。之后才打开的读端，宿主发 `proc.publish_endpoint@1` 补登记。
- 别的进程用 `Lookup` 查，只查得到 RUNNING 的进程的地址。
- 写端没有读端可写时才去查，两次查询至少隔 `ipc.lookup_retry_s`（默认 0.1 秒）。连上以后，正常收发时不查。
- 共享内存环的名字：宿主经进程管家把 `AllocShm` 转给本机节点代理；节点代理记下名字，进程退出后删掉这个环。

**顺带修正的流行为**：
- TCP 的 `read(0)` 原来每次空读固定等 10 ms，现在只看一眼；
- TCP 读端看到对端断开时，先读完已经到达的记录，再报 `PeerLost`；
- 共享内存的写端每次写之前先检查读端，读端已经关闭或心跳超时就报 `PeerLost`，不再先把一个没人读的环写满。
- **心跳超时先问内核**（2026-11-11，`doc/framework-bugs/2026-11-10-a-long-gil-hold-looks-like-a-dead-peer.md`）：心跳是线程写的，进程里一个占住 GIL 的长调用会让它停写，对端就以为这个进程死了。现在共享内存的两端各在环的段上持有一把锁（读端锁第 0 字节，写端锁第 1 字节），这一端的描述符关掉或者进程不管怎么结束，内核都会放掉它。锁是 open file description 锁（`F_OFD_SETLK`，2026-11-12）：起先用的 POSIX 记录锁（`lockf`）属于进程，进程里关掉这个段的任何一个描述符都会把它在段上的锁全放掉，比如被拒的第二个写端关自己的描述符（Codex 的审查）。心跳超时、锁也没人持有，才算对端不在了；心跳超时但锁还被持有，对端是活着、在忙，接着等。卡死的进程不再由流来判定，交给调用方自己的时限（比如调度器的 `sched.step_timeout_s`）。只支持 Linux；拿不到锁时退回只看心跳。TCP 本来就由内核判定（keepalive、FIN/RST），不变。

**验收测试**：
1. 两种后端：写端 A 写完关闭，写端 B 接着写，读端按顺序收到全部记录，`generation` 是 2。
2. 两种后端：写端 A 被杀以后，写端 B 接管。共享内存上，A 的心跳超时之前 B 拿到 `RingBusy`。
3. 两种后端：A 留下没读的记录就关闭，B 抢在读端之前写了一条；读端按 A、A、B 的顺序读到，代数是 1、1、2。
4. 共享内存：
   - A 停住超过 `peer_timeout_s`（心跳也停了），B 仍然拿到 `RingBusy`；A 继续跑、写完、关闭以后 B 才接管。
   - A 通过检查以后、写字节之前停住，B 在这期间接管被拒，A 的记录完整到达。
   - A 被杀、进程结束以后，B 立刻接管。
5. TCP：
   - 被换掉的写端迟到的帧被丢掉；换了 17 次之后，第一个写端迟到的帧照样被丢掉；更早的写端的第一帧比更晚的写端晚到，也不会把流抢回去。
   - 旧写端的尾巴和新写端的积压都超过 `stream_hwm`，也一条不丢、按顺序到达；调用方每次读之前都停顿得比 `peer_timeout_s` 还久，也一样。
   - 两个写端同时一直写，超过 `stream_hold_bytes` 就报 `PeerLost`；之后反复 `read`，每次都报同样的错，缓冲区不再增长。
6. 不可替换的 TCP 读端遇到第二个写端，报 `PeerLost`。
7. `Channels`：
   - 读端只登记一次；
   - 写端在读端登记前返回 False，查询有退避；
   - 读端所在的进程被换掉后，写端重新查到新读端；
   - 没人监听的 TCP 地址，`write` 立刻返回 False、不加 `generation`；
   - 读端被杀后留下的环，写端不接管、不加 `generation`。
8. 真实进程：进程管家先后重启读端所在的进程和写端所在的进程，数据都能接着流，每个连接内记录不丢、不乱序（`tests/framework/cluster/test_channels.py`）。
9. 真实进程：CheckIn 之后才打开的读端，环名经进程管家向节点代理申请，地址由宿主补登记，写端能查到它。
