# 状态单元的变更：排空与版本迁移

- 日期：2026-11-07
- 状态：**只有规格，实现留到阶段 2**（发起人 2026-11-07 决定）。接口要等真调度器、真 KV 来检验，现在用玩具单元实现很可能返工。
- 对应：modules.html “三类模块”里状态单元的重载规则（“v0 默认先排空再重建；提供迁移函数的可以不排空”）和动作阶梯下面那句（“只有会影响在途请求的动作才排空，而且只排空受影响的那部分请求”）；[change.md](change.md) 4.2 第 4 步；[control-plane.md](control-plane.md) §4、§9。
- 标注“（待确认）”的地方还没有和发起人确认。

## 1. 要解决的问题

一次变更要毁掉在途请求依赖的状态时，怎么办。会毁掉状态的有三种动作：
- **重启进程**（第 5 级：native 扩展、mesh、放置变了）：进程里所有状态单元的内容都没了。
- **重载状态单元**（它的代码或清单变了）：现在是卸掉旧实例、建一个空的新实例，内容全丢。
- **删除状态单元**。

## 2. 状态的种类

| 种类 | 例子 | 丢了会怎样 |
|---|---|---|
| 缓存 | paged KV 的页、前缀树、录好的 graph | 变慢，能重算 |
| 事实 | 请求表：谁发了什么、采样参数、已生成的 token、流式连接 | 用户看到出错，算不回来 |
| 统计 | EPLB 的负载统计 | 影响很小 |

框架不猜种类，看单元的声明：`[state] drain_on_reload`（已有，默认 `true`）表示“重建它会影响在途请求，重建前要排空”。缓存的使用者能自己重算的（比如前缀缓存），可以声明 `false`。

## 3. 分工

- **框架**（`core.change`，以及做影响分析的 `core.deps`）只做这些：
  - 判断什么时候要排空、影响到哪些；
  - 给通知和期限；
  - 按顺序调用单元的钩子，失败时撤回；
  - 把单元报告的结果记下来。
- **持有请求的单元**（调度逻辑）决定请求怎么处理：停止接收新请求、等在跑的跑完、中止、退回排队重算、挪到别的调度域……这是调度策略，可以做成策略单元，让 agent 去改。
- **状态单元**决定自己能不能迁移、怎么导出导入。

## 4. `core.deps` 怎么选

对每个会被重建或丢掉的状态单元实例，按顺序选第一条成立的：

1. 没被这次变更碰到：什么都不做。
2. 它的代码或清单变了，新版本声明能从旧版本迁移（§6）：在暂停期内迁移，不排空。算第 4 级（状态动作）。
3. 声明了 `drain_on_reload = false`：直接重建，不排空。
4. 其他情况：先排空（§5），再重建。

重启进程时，进程里所有状态单元按第 3、4 条处理，因为 v0 不做跨进程迁移。dry-run 给出每一处的选择，`notes` 里写明原因。

## 5. 排空

### 5.1 谁来排空、收到什么

- 持有在途请求的单元在清单里声明自己能排空：`capabilities.actions` 加上 `drain`（实现时给 `StateAction` 加这个值）。这种单元一般在调度宿主上（拓扑里 `leads_epochs` 的角色），不在要重启的 worker 上：worker 只知道自己的 KV，只有调度器知道哪些请求会受影响。
- `core.deps` 给**受影响的调度域**的领头进程里、声明了 `drain` 的单元生成排空动作（`ProcActions.drain`）。“受影响”指这个域里有进程要重启或停掉，或者有 `drain_on_reload = true` 的状态单元要重建、而且不能迁移。别的调度域不排空（DP）。
- 参数只给**事实**，不给指令：
  ```python
  {"restart": ["host-b/worker/1"], "stop": [], "rebuild": [{"unit": "kv.paged", "procs": ["host-a/worker/0"]}]}
  ```

### 5.2 钩子

框架里已经有这些钩子（2026-11-07 把期限钩子改成中性的了）：
- `start_drain(args)`：开始排空，单元自己决定怎么做。
- `drained() -> bool`：每个安全点问一次；返回 `True` 表示受影响的请求都处理完了。
- `drain_deadline() -> dict[str, int]`：期限到了（`change.drain_timeout_s`，默认 10 秒，计划可以覆盖），单元按自己的策略处理剩下的请求，返回每种结果各有多少个，例如 `{"aborted": 2, "requeued": 5}`。框架原样记进 `ChangeResult.drain_outcomes`。

**实现时要补的框架缺口**：排空动作现在不会收到 `commit()` 和 `abort()`。参与者撤回时，只调准备动作的 `abort()`；提交时，只调准备动作的 `commit()`。所以排空以后变更如果撤回，持有请求的单元不知道要恢复接收请求。排空动作也要收到这两个调用：
- 撤回：恢复正常；
- 提交：变更完成了。

### 5.3 框架不做的

- 不碰请求，不知道有哪些请求，不决定请求的命运；
- 不替单元选“中止还是退回排队”。

## 6. 版本迁移：状态单元的代码改了

### 6.1 做法：导出，再导入

- 旧实例 `export_state()`：返回一个进程内的对象，内容是纯数据（dict、list），加上设备缓冲区的引用。张量本身不拷贝，也不序列化、不跨进程。
- 状态单元声明自己状态的格式版本：`[state] schema = N`（整数）。新版本声明迁移函数和它能从哪些格式迁过来：`[state] migrate = "mod:function"`、`migrate_from = [N - 1, N]`。
- 在暂停期内、变更的 Execute 里，按这个顺序：
  1. `exported = old.export_state()`；
  2. 卸掉旧实例：它放掉自己的引用。`exported` 还引用着设备缓冲区，所以显存不会被释放。规则：`teardown` 只能放引用，不能显式释放已导出的缓冲区；
  3. 建新实例，`state = function(exported, from_schema)`，再 `new.import_state(state)`；
  4. 任何一步失败就撤回：装回旧版本，`old_version.import_state(exported)`。契约：导出再导入，结果和原来一样。
- 代价只有 Python 侧重建索引的时间（毫秒到百毫秒级），没有显存拷贝。

### 6.2 不能迁移的时候

- 显存布局变了（页大小、数据类型、头的排布）。要么迁移函数做一次转换拷贝，临时要两倍显存；要么新版本不声明能从旧格式迁移，走排空加重建。v0 建议后者。
- `core.deps` 静态判断：旧版本的 `schema` 在不在新版本的 `migrate_from` 里。dry-run 就能看出会不会排空。

### 6.3 跨进程

进程重启时不迁移，v0 不做跨进程迁移。

## 7. 和已有名字的冲突（待确认）

状态动作里已经有一个 `migrate`（`StateAction`）。它的意思是在同一个版本内搬内容，比如场景⑤里 EPLB 在 rank 之间搬专家，和这里的“版本迁移”不是一回事。本文把版本迁移的钩子叫 `export_state` / `import_state`，清单字段沿用已有的 `[state] migrate`（modules.html 里叫“迁移函数”）。实现时建议给状态动作的 `migrate` 换个名字，比如 `relocate`。

## 8. 验收测试（实现时）

1. 重启 worker 之前，调度宿主上的排空单元收到事实。期限内处理完的不进结果；期限到了，单元按自己的策略处理剩下的，结果原样记进 `drain_outcomes`。
2. 排空以后变更撤回：排空单元收到 `abort()`，恢复接收请求；提交时收到 `commit()`。
3. `drain_on_reload = false` 的状态单元重建时不排空。
4. 请求表的代码改了、带迁移函数：在途请求不丢，设备缓冲区还是同一块（地址不变）。
5. 迁移失败：撤回以后，旧实例装回原来的内容。
6. 布局变了（旧 `schema` 不在 `migrate_from` 里）：走排空加重建，dry-run 就能看到。
7. 只排空受影响的部分：两个调度域（DP）里只有一个域的进程要重启时，只排空那个域。

## 9. 留到阶段 2 写真调度器、真 KV 时再定

- `export_state()` 返回对象的具体形式；张量之外的设备资源（CUDA graph、通信组）怎么处理。
- 调度宿主自己重启时，前端的连接怎么保住（不在本文范围）。
- PD 分离、DP 下“受影响的请求”怎么描述。
