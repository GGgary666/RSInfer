## 2. 要解决的问题

用户的想法：v1 要支持 DS 1017 的 EP，多卡通信单独做成一个部分，考虑把多机（v2）的东西也并进这个部分：先上多机多卡，再适配 DS 1017。

**目的：DS 1017 的时候少踩坑，降低试错成本。**

## 3. 讨论过的方案和评估（Claude 的意见，未定）

### 3.1 多机并不并进多卡这部分

- 建议**只并和模型无关的那一半**：⑥ 页的第 3–9、11 步，也就是改拓扑、快照分发、跨机步通道、建通信组、按机器放权重、一台机器丢失。
- DeepEP internode、分层 EPLB、跨机搬专家（⑥ 的第 1、2、10 步）留在 DS 1017 之后。
- 理由：
  - 按 P7，单机是多机的特例，节点代理、TCP 通道、快照分发、跨机两阶段提交都已经有了，CI 里用两个节点代理测过，缺的是真 GPU、真模型上的验证。
  - 多卡和多机改的是同一批东西，分两次做要改两遍。
  - 阶段 2 写的单元从没在两台主机上跑过，在单元还少的时候查出违反 P7 的地方更便宜。

### 3.2 用什么当验证的载体

各方案能测到 DS 1017 的哪些分布式风险：

| 风险 | Qwen DP | Qwen TP | P/D 分离 | MoE 上的 EP |
|---|---|---|---|---|
| 多调度域：每个 rank 自己的 batch 和账本、路由 | ✓ | ✗ | 部分 | ✓ |
| 多机：真硬件上的 P7、跨机步通道 | ✓ | 勉强 | ✓ | ✓ |
| rank 之间直接通信（worker 之间建连、IB） | ✗ | ✓ | ✓（点对点） | ✓ |
| 步内 collective：通信组的建立和拆除、录进 graph、组内一起热改和撤回 | ✗ | ✓ | ✗ | ✓ |
| EP 特有：各 rank 的 batch 不同、每步数据量在变的 all-to-all、空 batch、组内对齐分桶 | ✗ | ✗ | ✗ | ✓ |
| 按 rank 放不同的权重 | ✗ | ✓ | ✗ | ✓ |

- **只做 DP**：rank 之间不通信，最可能踩坑的"通信组 × 热改 × graph × 撤回"留到 DS 1017 上才第一次碰到。
- **TP**：测得到 collective，但形状固定、各 rank 的 batch 相同，EP 特有的那一行测不到。TP 在模型侧的活（切线性层、GDN、KV）DS 1017 用不上。我们的引擎里现在没有 TP 代码。
- **P/D 分离**：
  - 是 rank 之间直接通信，但形状是每个请求一次的点对点，异步、不进 graph，替代不了 EP 的验证。
  - SGLang `e838360` 的 P/D 带 GDN 状态的传输（`disaggregation/prefill.py` 的 `StateType.MAMBA`）。
  - 用户定了先不做。
- **小 MoE 模型上的 EP**（例如 SGLang 的 `qwen3_moe.py`，有标准和 DeepEP 两种 `token_dispatcher`）：形状和 DS 1017 一样，模型简单，出了问题就是分布式的问题。
- **截小的 DS 1017**：用户的看法是，与其支持一个小的 Qwen-MoE，不如直接拿一两层 DS 1017 做。Claude 同意。模型问题和分布式问题靠顺序分开：先把单 rank 的 DS 1017 做对，再上 DP 和 EP。

最后一轮的倾向是截小的 DS 1017，**没有定**。

## 4. 单卡的 agent 能做多少

| 内容 | 单卡（4090 D） | 要多卡的 agent |
|---|---|---|
| 调度：多调度域、组内同步走、空 batch、路由、组内对齐分桶 | 全部，CPU 上测 | 无 |
| DS 1017 的模型和层、MoE 流水线、新的状态种类、nextn 投机、前缀规则、前端 | 单 rank、参照 kernel、截小的结构 | 全尺寸的权重和对齐 |
| kernel | definition 和 PyTorch 参照实现 | 真 kernel（FP8、FP4、压缩 attention 等，SM100 才能跑） |
| EP 的通信 | 参照版 dispatch：两个 worker 进程放在同一张卡上，数据经主机内存交换。能验证 EP2 对 EP1 的输出、组内同步、杀掉一个 rank、热改和撤回 | NCCL、NVSHMEM、DeepEP |
| 带 collective 的 CUDA graph | 只有协调录制的逻辑，用假平台测 | 真的录制和回放 |
| EPLB、Engram | 策略和搬迁的逻辑，小表 | 真负载、RDMA |
| 多机、DP8 的吞吐、rank 对应的卡 | 无 | 全部 |

单卡的硬限制：
- NCCL 不允许两个 rank 在同一张卡上，单卡上的 collective 只能走主机内存。
- 走主机内存的通信录不进 CUDA graph，"graph 里的 collective"在单卡上一步都走不到。
- 一层的 384 个专家在 bf16 下约 27 GB（按 config 估），单卡上除了截层数还要截专家数。FP4 放得下，但 4090 D 跑不了 FP4 的 kernel。

和 Qwen 那次的差别：
- Qwen 时，4090 D 能跑真 kernel（FlashInfer、Triton），MTP 里开重叠的那个 bug 就是在单卡上查出来的。DS 1017 的真 kernel 和通信库单卡上都跑不了，"通信组 × 热改 × graph"这类坑会落在多卡的 agent 那边。
- 能做的是把这部分压小：参照版的通信组和真的通信组走同一套单元生命周期（每进程只能初始化一次、组员重启要全组重建、撤回时怎么拆）。这样生命周期的逻辑 bug 在单卡上就能查出来，留给多卡的只剩库本身的问题。
