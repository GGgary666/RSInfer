## 2. 盘点结果

来源：SM100 上一个不占 GPU 的任务（`20261114T070433Z-6376b23c`），读了 checkpoint 的小文件和 safetensors 头、节点上的工具；本地读了 DeepInfer（`~/DeepInfer`，`a679bb8`）和 checkpoint 自带的参照实现。

### 2.1 模型结构

`config.json` 的 `text_config`，加上参照实现 `inference/model.py`：

- **主干**：40 层，hidden 5120，词表 129280。
- **残差流是 4 份**（Hyper-Connections，`hc_mult = 4`）：每个子层前把 4 份合成 1 份，子层后再展开，混合系数由残差流自己算出来，其中一组用 20 轮 Sinkhorn 归一，fp32。
- **attention**（每层都有）：
  - 64 个头，每头 512 维。每个 token 只存一个 512 维的 latent，K 和 V 是同一个。
  - Q 走低秩（1280），输出投影分 8 组、低秩（1024）。RoPE 只转最后 64 维。
  - 一次稀疏 attention 同时看两个来源：最近 128 个 token 的原始 KV（滑动窗口，SWA），加上 indexer 选出的最多 512 个压缩位置。
- **层分三类**（`compress_ratios`、`kv_source_layer_ids`、`index_source_layer_ids`）：

  | 层 | 压缩 KV | 谁产生压缩 KV | 谁跑 indexer |
  |---|---|---|---|
  | 0–1 | 没有，只有窗口 | — | — |
  | 2–19 | 2 个 token 压成 1 个 latent（带门控的 softmax 池化） | 第 2、8、14 层，各管后面 6 层 | 第 2、8、14 层，后面的层直接用它选出的位置 |
  | 20–39 | 1 个 token 1 个 latent | 第 20 层，管 20 层 | 第 20、24、28、32、36 层；第 20 层另外先选 2048 个候选块（每块 8 个位置），后面的 indexer 只在候选块里选 |

  DeepInfer 把前 20 层叫 encoder、后 20 层叫 decoder：后 20 层的块 KV 都来自第 20 层。
- **MoE**（每层）：384 个路由专家加 1 个共享专家，每个 token 选 6 个，打分函数 `sqrtsoftplus`，SwiGLU 带上限 10。
- **Engram**：第 1、14 层之前，各查一张约 3.84 亿行 × 256 维的 n-gram 哈希表（最长 4-gram，8 个头），按门控加进残差流。它在主 forward 里，跳不过去。
- **DSpark（nextn）**：主干后面另有 3 层（128 个专家选 3 个），一次起草 5 个 token；有 Markov 头和置信度头。输入是第 37–39 层 attention 的输入。
- **量化**：
  - 稠密权重是 FP8（e4m3），每 32×32 一个 ue8m0 scale。
  - 路由专家是 FP4（每 32 个一个 ue8m0 scale，一个字节放两个值）。
  - 激活进 GEMM 之前动态量化成 FP8。
  - 存下来的 KV 也是量化的：窗口 KV 是 FP8，压缩 KV 和 indexer 的 K 是 FP4。
- **视觉**：32 层 ViT 加 aligner。v1 不加载。

### 2.2 权重有多大

一共 475.2 GiB，48 个 safetensors，96,085 个张量。

| 部分 | 大小 | DP4 + EP4 时每张卡 |
|---|---:|---:|
| 路由专家（40 层 × 384 个，FP4 加 scale） | 268.9 GiB | 67.2 GiB（按 EP 分） |
| Engram 的两张表（FP8 加 scale） | 188.8 GiB | 47.2 GiB（按行分 4 份）；或者放主机内存 |
| 主干其余部分：attention、共享专家、gate、HC、norm | 6.7 GiB | 6.7 GiB（每卡一份） |
| embedding 和输出头 | 2.5 GiB | 2.5 GiB（每卡一份） |
| DSpark 的 3 层 | 7.4 GiB | 约 2.4 GiB（专家按 EP 分） |
| 视觉 | 0.9 GiB | 不加载 |

- 一个专家约 18.8 MB，一层的路由专家约 6.7 GiB。
- **一张卡放不下整个模型**（光路由专家就 269 GiB，一张卡 179 GiB）。
- **4 张卡放得下，Engram 也可以直接放在显存里**：每卡约 126 GiB，剩 50 GiB 以上。Engram 放主机内存的话每卡约 79 GiB。
- 2026-11-13 我按 config 估的"一层专家 bf16 约 27 GB"是没量化的大小，实际存的是 FP4。

### 2.3 状态有多大

按 DeepInfer `worker/cache_engine.py` 的布局算：

| 状态 | 内容 | 大小 |
|---|---|---:|
| 窗口 KV（SWA） | 43 层各一个环：128 个 token，另加 6 个给投机回退；每 token 528 B | 每个请求约 2.9 MiB，固定 |
| 压缩块 KV | 只有 4 个来源层有；每个 latent 288 B | 每 token 720 B |
| indexer 的 K | 同样 4 个来源层；每个 latent 68 B | 每 token 170 B |
| 压缩的累加器 | 3 个压缩比为 2 的来源层，没凑满一组的尾巴，fp32 | 每个请求几十 KB |

- 随上下文长度增长的只有每 token 890 B：1 GiB 能放约 120 万 token。
- DS 1017 的状态很小，显存主要给权重。

### 2.5 有哪些可以对照的实现

| 实现 | 是什么 | 在哪能跑 | 缺什么 |
|---|---|---|---|
| checkpoint 自带的 `inference/`（MIT） | DeepSeek 官方的可读参照实现：`model.py` 1312 行，6 个 TileLang kernel（FP8 GEMM、FP4 GEMM、稀疏 attention、Sinkhorn、两种量化）。支持按 rank 切分 | **4090 D 上能跑**（见下） | 缓存按 batch 行和最大长度预分配，不分页；batch 里的序列要等长、同步走；没有投机的循环、没有 EPLB |
| DeepInfer（Apache-2.0） | 生产实现：FlashMLA、DeepGEMM、DeepEP、TileKernels、DeepSelect 和自己的 TileLang kernel；attention DP、MoE EP 加 EPLB、DSpark 变长验证、CUDA graph、batch-invariant 模式 | 只支持 SM100（SM100）；要 torch 2.13.0+cu132、NCCL 2.32.3 | 没有 KV 缓存系统（前缀缓存）、没有 HTTP 服务；调度的热路径（块管理、输入元数据、输出处理）在 C++ 里（`csrc/engine`） |
| SGLang `e838360` 的 `deepseek_v4*` | 模型 1 万多行，加专用显存池 | 没试 | 只在 DeepInfer 没有的部分用（前缀缓存、服务侧） |

**本地验证过**：把 `inference/` 拷到 4090 D，装 tilelang 0.1.12，跑它的自测 `python model.py`（小模型：5 层加 1 层 DSpark、8 个专家，prefill 128 个 token 再 decode 22 步，稠密 FP8、专家 FP4 的 kernel 都用上）。
- 通过。首次编译 kernel 约 70 秒，之后 5 秒；显存峰值 1.1 GiB。
- 用的是本地现有的 torch 2.11.0+cu130。

所以本地有一份能跑真量化 kernel 的官方实现可以当真值。DeepInfer 在本地跑不了。

[v1-distributed.md](v1-distributed.md) 第 4 节写的"4090 D 跑不了 FP4 的 kernel"，对生产 kernel（DeepGEMM）成立，对官方参照实现的 TileLang kernel 不成立。

## 3. 状态种类：现有接口装不装得下

这是 modules.html 说的最大风险，结论是**大体装得下，要补的都在单元这一层，目前没看到要改框架本体的地方**。

现有的声明（`core/contracts/state.py` 的 `StateDecl`）有：种类、层、每项的张量形状和 dtype、生命周期（按请求分页，或每请求一个固定槽）、每页几个 token、每隔多少 token 留一份快照。

| DS 的状态 | 怎么声明 | 说明 |
|---|---|---|
| 窗口 KV | 槽，每层一项，`snapshot_every = 128` | 和 Qwen 的 GDN 槽同一类。快照比 GDN 简单：位置 p 的窗口就是最后 128 个 token 的 KV，没有递推 |
| 压缩块 KV、indexer 的 K | 按请求分页，一页 128 个 token | 只有 4 个来源层声明；压缩比 2 的层一页放 64 个 latent，压缩比 1 的放 128 个 |
| 压缩累加器 | 槽 | 128 是 2 的倍数，快照边界上累加器是空的，不用存 |
| 跨层借用 | 不用声明 | 只有来源层声明，模型把来源层的张量交给后面的层 |
| Engram 的表 | 不是请求状态，是权重 | 走权重的放置（按行分给各 rank，或放主机内存） |

要补的：

1. **dtype**：声明里要能写 u8、FP8、FP4。
2. **投机被拒以后的回退**：
   - Qwen 是"先算中间状态，接受了再提交"（`gdn.commit_states@1`）；DS 是环里多留几个位置，拒了就把写指针退回去。
   - executor 的投机路径现在假定前一种，要改成每种状态自己决定怎么回退。
3. **DP 的账本**：
   - 现在多 rank 是 TP 的语义：每个 rank 收同一份计划，容量取各 rank 的最小值，token 用 rank 0 的（`core/sched/README.md`）。
   - DP 下每个 rank 是一个调度域，有自己的请求和自己的账。这是 `core.sched` 和账本要做的最大的一块。
4. **前缀缓存的命中规则**：
   - 命中长度由块 KV 决定，是 128 的倍数；窗口 KV 的快照缺了，就退一个块、重算最后 128 个 token。
   - 重算时只重建窗口 KV，不重写块 KV。这是现在的每步计划里没有的东西，`StepPlan` 可能要加一项。
   - 后 20 层的窗口 KV 不进缓存，每次 prefill 重算：精确的做法要把最后 2560 个 token 过后 20 层；DeepInfer 只重算 128 个，是近似（它叫 SWA bounded replay）。
5. **拓扑**：`Mesh` 现在写的是 `{"tp": 1}`，`RankPlacement(rank, host, gpu)` 已经能给每个 rank 指定卡。改成 `{"dp": 4, "ep": 4}` 是数据，但没实际跑过多个 worker 各占一张卡。

## 5. 阶段

原则：先把单 rank 的模型做对，再上多卡。这样出了问题能分清是模型的还是分布式的。每个阶段单独开 PR，开发照旧在跑着的引擎上热改。

### 阶段 1：单 rank 的小模型（本地）

1. kernel 的 definition 和纯 PyTorch 参照，逐个对照官方的 TileLang kernel。
2. 两种权重格式，加一个小配置的随机 checkpoint 生成器。
   - 小配置保留真实的维度（hidden 5120、64 头 × 512），这样 kernel 的形状是真的。
   - 减少的是层数、专家数和 Engram 表的行数。
   - 层要重新编号，让三类层、来源层和借用层、候选块、Engram、DSpark 每样至少出现一次。
3. 模型、层、状态单元装进 worker 栈：先 eager 单请求，再 batch，再 decode graph。

**验收**：小配置上，同一份随机权重，引擎和官方参照实现的 logits 在容差内、贪心 token 相同（平局单独分析，见 7.2）；eager 和 graph 一致。

### 阶段 2：真 kernel 和真权重（SM100，单卡）

1. 在 `/workspace/agxinfer-env` 里建自己的环境，把 DeepInfer 和它的 vendor 库编出来。
2. 生产 solution 逐个对照参照 solution，每个一个 pytest，按批提交任务。
3. 真权重：单卡放不下整个模型，取前几层连同它们的专家，对照官方参照实现的中间结果。
4. 做一个"会话式"任务：起一次引擎，轮询分支，每次 push 就 apply。SM100 上也能热改，不用每次冷启动。

**验收**：每个生产 kernel 有对照记录；真权重的前几层和参照实现一致。

### 阶段 3：多卡，DP4 + EP4

1. 本地，CPU 上测：
   - `core.sched` 的多调度域；
   - 同一个 EP 组的 rank 每步一起走，没请求的 rank 跑空 batch；
   - 每个域一本账；
   - DP 路由。
2. 本地，4090 D：
   - 通信组单元，配一个参照版 dispatch：两个 worker 进程放在同一张卡上，数据经主机内存交换。
   - 验证 EP2 和 EP1 的输出一致、杀掉一个 rank、热改和撤回。
3. SM100：
   - 换成 NCCL 和 DeepEP，decode graph 里带通信。
   - 先小模型 2 卡，再整模型 4 卡。

**验收**：整模型在 4 张卡上，同一组提示词的输出对照 DeepInfer（开它的 batch-invariant 模式），并测吞吐。

### 阶段 4：v1 的后半

DSpark 投机、前缀缓存的 DS 规则、EPLB、前端（提示词格式、reasoning 和工具调用的解析）。顺序到时候再排。

## 7. 没把握的地方和要定的事

### 7.1 风险，按影响排

1. **通信组和热改、graph、撤回放在一起**。DeepEP 的 buffer、NVSHMEM 每个进程只能初始化一次、一个 rank 重启以后整组要重建。这部分只有 SM100 上能真跑，是最可能卡住的地方。
2. **DP 调度域**。工作量大，但逻辑都能在本地 CPU 上测。
3. **SM100 上的环境**。DeepInfer 钉的是 torch 2.13.0+cu132 和 NCCL 2.32.3，节点上是 CUDA 13.0 和 torch 2.11。vendor 库能不能在节点上编出来、PyTorch 的 cu132 轮子镜像里有没有，要试了才知道。
4. **Engram 在多 rank 下每次 forward 都要跨 rank 取行**（表按行分在各 rank 上）。所以多卡以后，第一个进 graph 的通信不是 MoE 的 dispatch，而是 Engram。
5. **投机的回退方式和 Qwen 不同**（第 3 节第 2 条），executor 的投机路径要改得更通用。
6. **前缀缓存的"只重建窗口"**可能要改每步计划的定义（第 3 节第 4 条）。
7. **多个 worker 各占一张卡没实际跑过**（第 3 节第 5 条）。

### 7.2 我提的默认做法，不同意请指出

1. **本地的真值用 checkpoint 自带的官方参照实现。**
   - DeepInfer 在 4090 D 上跑不了。
   - DeepInfer 仍然是搬运的基准，也是 SM100 上对齐输出和比性能的对象。
2. **"对齐"的验收标准**：
   - 同一份权重、同一组提示词，logits 在容差内，贪心 token 逐个相同。
   - 不同的位置逐个看：两个候选的 logit 差在量化误差以内的算平局，不算错。
   - 理由：2026-11-14 Qwen 的 bf16 测试在 SM100 上就因为平局挂过。
3. **SM100 上给 DS 单独建一个环境，版本跟 DeepInfer 走**（torch 2.13.0+cu132）。
   - Qwen 用的环境不动。
   - 本地 4090 D 仍是 torch 2.11，两边版本不同。
4. **投机先做固定长度的验证（一次验 5 个），变长验证放后面。** DeepInfer 的变长验证要在 GPU 上重排每个请求的验证长度，和我们现在"CPU 上定好每步计划"的做法差得比较远。
5. **Engram 的表先放显存**（4 卡放得下）。主机内存加 RDMA 读取以后再说。
6. **前缀缓存先做精确的**（后 20 层的窗口按 2560 个 token 重算）。DeepInfer 的近似重算做成一个开关，后面再加。

### 7.3 要用户定的

### 8.2 和计划不一样的地方

1. **本地的小配置用的是小形状，不是真实形状。** 参照实现的 attention kernel 在 64 头 × 512 维时，每个线程块要 138 KB 共享内存，4090 D（SM 8.9）只有 99 KB。本地用它自带的小形状（1024 宽、16 头 × 128），真实形状放到 SM100 上（第 9 节）。
2. **参照 kernel 做成了 batch 无关的。** 这不在计划里，是测出来必须做的：
   - 随机权重的模型对末位极其敏感：换掉任何一个 kernel 的末位，8 层之后 logits 差 0.3 到 0.7（幅度约 4），再走几步就是另一串 token。
   - torch 的矩阵乘和归约的末位随行数变（GPU 上 `F.linear` 85% 的元素、`mean` 在 16 行以下；CPU 上 `exp`、`sigmoid` 也随张量大小变）。
   - 所以参照 kernel 自己按固定顺序求和（`total`）、每行单独相乘（`matmul`），CPU 上把不精确的逐元素函数按行算（`each`）。代价是慢，参照本来也不为快。
3. **参照实现调用 torch 的地方单独留了一份。** 它的 `F.linear`、einsum、`mean`、`topk` 和它的 TileLang kernel 一起注册成后端 `tilelang`。用这个后端，引擎算的就是参照实现算的。
4. **窗口那一段的列数固定是窗口宽度。** 参照实现 prefill 一个比窗口短的提示词时，只列提示词那么多列，后面压缩 key 的列号跟着变。引擎要让提示词不管怎么分块结果都一样，所以总是列满窗口宽度。提示词比窗口短时，这一点让引擎和参照实现在末位上不同（key 是同样的 key）。

- **17 个 kernel 都能录进 graph。** `ds.moe_experts@1` 平时按这一步实际要的行数排（要读一次设备），录进 graph 的是固定行数的版本（`deepinfer.fixed.ds.moe_experts@1`）。官方参照实现的 TileLang kernel 之前标的是不可捕获，没有重新验。

**算术上和官方参照实现不一样的三处**（都不是累加顺序的问题）：
1. **MoE 少一次舍入。** DeepInfer 的 kernel 把 SwiGLU 的结果直接从 fp32 量化成 FP8；官方参照实现先舍入到 bf16 再量化。先舍入会让大约 1/16 的值落到相邻的 FP8 值上，专家输出的和因此最多差几个百分点（真权重上最大 4.9%）。参照 kernel 加了一个不属于 definition 的开关 `direct=True`，按 DeepInfer 的算法算，测试拿它对照。
2. **HC 系数用 TF32 的乘法。** 系数差到 1e-4 量级。
3. **FP4（e4m3 scale）在恰好一半处的舍入。** TileKernels 乘 scale 的倒数，参照是除以 scale；`x / scale` 恰好是 2.5 或 5 时落到另一边。约万分之五的元素差一个 FP4 台阶。

**权重布局改了**（照 DeepInfer 在加载时做的）：
- 一层的专家从三叠（`w1`、`w2`、`w3`）改成两叠：`w13`（每个专家的 `w1` 在上、`w3` 在下，一次乘法出 SwiGLU 的两个输入）和 `w2`。
- 专家的 scale 只存 GEMM kernel 读的那种排法（每行每 32 个值一个 scale，四个指数拼成一个 int32，按列存；`formats.pack_scales`）。FP8 权重在 checkpoint 的 32 × 32 块 scale 旁边多存一份这种排法的（权重字节数的 1/32）。
- 这些都是模型声明的张量，由 `load_weights` 填，所以 `refit` 会重新写它们，graph 里录的地址不变。没有放在 kernel 单元里做缓存，就是因为 refit 之后没人通知它。
- 我们自己用 torch 排的结果和 `deep_gemm.transform_sf_into_required_layout` 的输出逐位相同。

### 9.3 状态换成 DeepInfer 的字节布局（2026-11-14 晚）

三种状态现在存的都是字节，格式照 DeepInfer 的 `tilelang_ops/cache_common.py`（FlashMLA 的接口文档写的也是这个）：

| 状态 | 一条记录 | 存在哪 |
|---|---|---|
| 窗口 KV（`ring`） | 528 B：512 个 e4m3 值，后跟 16 个 ue8m0 scale（每 32 个值一个） | 每个请求的槽 `[槽, 128, 528]`，一个槽就是 FlashMLA 的一个块 |
| 压缩 latent（`kv`） | 288 B：256 B 的 e2m1 值（一个字节两个，低半字节在前），后跟 32 个 e4m3 scale（每 16 个值一个） | 分页，`[token 槽, 288]` |
| indexer 的 key（`ik`） | 68 B：64 B 的 e2m1 值和 4 个 ue8m0 scale | 分页；一页里先放整页所有 key 的值，再放整页所有 key 的 scale |

- 记录里的值就是原来存的那些量化后的值：打包再解包逐位还原（`tests/units/kernels/test_ds1017.py`）。所以换布局以后，**后端 `tilelang` 的引擎仍然和官方参照实现逐位相同**（本地小形状 340 步和 541 步；SM100 真实形状 16 步、真权重前 8 层 16 步）。
- 状态比原来小：窗口 KV 每 token 从 1024 B 降到 528 B，latent 从 1024 B 降到 288 B，key 从 256 B 降到 68 B。
- 打包和解包在 `kernels/ds1017_formats.py`（`pack_kv`、`pack_latent`、`key_sections` 等），纯 torch。

**decode 直接在缓存的字节上做 attention**，新 definition `ds.cache_attn@1`：
- decode 步先把这个 token 自己的 KV 写进环，再让 attention 按记录号读窗口的缓存和 latent 的缓存，不再每步把要看的 key 收集成 bf16。
- 后端 `deepinfer` 用的是 **FlashMLA 的 decode kernel**（`flash_mla_with_kvcache`）：窗口的 FP8 记录是主缓存，latent 的 FP4 记录是 extra 缓存，开 `enable_batch_invariant`。和参照在容差内；一个 token 的结果不随同一步的其他行变；能录进 graph。
- 参照和后端 `tilelang` 把记录读出来再算，结果和改之前逐位相同。
- prefill 步不变：这一块自己的 key 还没进缓存，仍然用 `ds.sparse_attn@1`，窗口里更早的 key 从环里解出来。

**窗口 KV 的打包**也是一个 definition（`ds.pack_kv@1`）：后端 `deepinfer` 用 TileKernels 的一次 `per_token_cast`，出来的字节和参照逐字节相同。decode 步不再先做一次 fake-quant 再打包。

|---|---|
| `tests/gpu/test_ds1017_deepinfer.py`（现在 60 个） | 全过（分支头上最后一次：任务 `20261114T161244Z-dee832cf`）。新加的：FlashMLA 的 decode kernel 对参照（带和不带 latent 的缓存）、TileKernels 打包对参照（逐字节相同），各自的"不随其他行变"和 graph 回放 |

| 配置 | 单流 | 8 路并发 | 换布局之前 |
|---|---|---|---|

- **换成字节以后慢了约 6%。** decode 的 attention 不再收集 key 了，但多出来的打包和解包里，只有窗口 KV 的打包是一次 kernel；压缩 latent 和 indexer key 的打包、indexer 每步把 key 解回数值，还是一串 torch 操作（每个几十次启动）。纯 torch 打包窗口 KV 时更慢（随机权重 6 层，graph 回放 4.7 ms 一步；换成 kernel 以后 4.0 ms；换布局之前 3.5 ms）。

### 9.4 DeepInfer 自己的算子和 DeepGEMM 的 indexer（2026-11-14 夜）

照 DeepInfer 自己的做法接，融合的大 kernel 先不上。

**latent 的分页照 DeepInfer 改了。** 原来压缩 latent 和 indexer key 放在它第一个 token 的槽上，压缩比为 2 的层有一半的槽空着，DeepGEMM 的分页 indexer 读不了。现在和 DeepInfer 的 `ca_cache`、`ica_cache` 一样，一页（128 个 token）放 `128 / ratio` 条：

- 第 `j` 个 latent 的行号是它第一个 token 的槽号除以 ratio。页号沿用 token 的页表，不另分配。
- `state.kv_paged` 允许一个张量每页的条目数少于每页的 token 数（Qwen 的照旧，每 token 一条）。
- 压缩器没凑满的组照 DeepInfer 的 `ca_state` 存成 `cstate [ratio, 2, dim]`（每个成员的 score 和 KV）。
- DS 的页大小默认改成 128（DeepInfer 的 block）：`deploy/agxinfer.py --page-size` 不给时由模型族定，Qwen 仍是 16。

**新 definition**，都按 DeepInfer 模块的调用方式写。参照和 TileLang 后端用同一份组合（`kernels/ds1017_compose.py`），只换底下的算术，所以 TileLang 后端仍是官方的算术：

| definition | DeepInfer 后端用的 | 对应 DeepInfer 的 |
|---|---|---|
| `ds.rope@1`（改成 cos/sin 表加位置） | `fused_norm_rope_hadamard_cast_store_kvcache`（只开 RoPE） | `_q_b_norm_rope` 等 |
| `ds.transform@1` | 同上，norm + RoPE + FP8 cast back | `_prepare_swa_kv`（prefill） |
| `ds.store_cache@1` | 同上，写进缓存（`KVCacheOutArgs`）；只存值时 `store_kv_cache` | `_prepare_swa_kv`（decode）、`forward_store_kv_cache`、`store_index_kv` |
| `ds.load_values@1`、`ds.load_keys@1` | `load_paged_kv_cache` | prefill 的 `load_paged_kv_cache` |
| `ds.quant_index_q@1` | 同一个融合算子，RoPE + FP4 | `MQA._quantize_q` |
| `ds.index_topk@1`（prefill） | DeepGEMM `fp8_fp4_mqa_logits`，候选块的用户层 `fp8_fp4_sparse_mqa_logits`；`candidate_block_max`、DeepSelect、`restore_candidate_indices_inplace` | `MQA._topk_prefill` |
| `ds.index_topk_paged@1`（decode） | DeepGEMM `fp8_fp4_paged_mqa_logits` / `fp8_fp4_paged_sparse_mqa_logits`，同上，再 `convert_kv_index` | `MQA._topk_decode` |
| `ds.compress@1`、`ds.compress_decode@1` | `compress_and_update_state_prefill` / `_decode` | `Compressor.forward_pre_norm` |
| `ds.shared_expert@1` | 一次 FP8 GEMM 算 `w1`、`w3`，TileKernels `swiglu_forward_and_per_token_cast`，再一次 GEMM | `DeepseekMoE.shared_forward` |
| `ds.engram_hash@1` | TileKernels `engram_hash` | `NgramHashMapping` |

- DeepInfer 的 TileLang 算子搬到了 `engine/kernels/deepinfer/tilelang_ops/`（Apache 2.0，带 `LICENSE.deepinfer`）：算子本身原样，去掉了测试和 torch 参照，`PLATFORM` 换成只有 CUDA 的一个小类，两个模块级列表改成只读的。
- prefill 的 attention 照 DeepInfer 的做法：每层把要看的东西装进一个源里，即环里更早的窗口 KV、这一步的 KV、各行的 latent（按 load segments 装载），然后一次 sparse attention。原来是每个 token 各收集一份 key，`[tokens, keys, dim]`。
- 共享专家的 `w1`、`w3` 在装载时叠成 `w13`（连同 block scale 和 packed scale），和 DeepInfer 的 `shared_gate_up_proj` 一样。TileLang 后端仍按官方分两次乘（各取一半）。

**为了让 TileLang 只编译一次，和 DeepInfer 一样固定了几个宽度。** DeepInfer 总是传模型的最长长度，top-k 总是 512：

- decode 的分页 indexer 拿到每行到 `batch.max_context_len` 为止的全部页，kernel 的宽度按页数算。
- prefill 的 indexer 宽度用 `batch.max_context_len / ratio`。
- top-k 短于 512 时（短的上下文），给 TileLang 的候选恢复和 `convert_kv_index` 补到 128 的倍数（`convert_kv_index` 在 300 宽时 layout inference 失败）。
- 没固定之前，eager decode 每步要 9 秒（每步重新编译）。

### 9.5 没做的

- **融合的大 kernel 没接**（按用户的意思先不上）：`mega_moe`、`bf16_mega_gate`、`mega_mhc`、FlashMLA 的 `fused_norm_rope_attn_rope_cast`。DeepInfer 在 SM100 上走的是这些。`mega_moe` 要通信组，属于阶段 3。
- **Engram 的表查询**：DeepInfer 的 `EngramBuffer` 是按 engram 并行组分布式查表的，属于多卡。单卡上仍是 torch 的取行和反量化。
- DeepInfer 的元数据算子（`prepare_v4_decode_metadata`、`expand_swa_index`、`get_kv_*_index`、`kv_index_cat`、`gather`）：它们算的是 DeepInfer 自己的 `InputMetadata`。我们的层自己在设备上（decode）或主机上（prefill）算同样的索引，没有接。
- 还没有和 DeepInfer 本身比，要等整个模型（阶段 3 的多卡）。
- 真权重只覆盖到前 8 层的层种类。压缩比 1 的层（20 层以后）、候选块、第 14 层的 Engram 要多卡；这几种层在真实形状的随机权重上验过。

## 10. 阶段 3 做到哪了（2026-11-15）

分支 `dev/ds1017-ep`。用户 2026-11-15 定的：EP、EPLB、整个模型能生成有意义的文本、融合大 kernel 和还没接的 kernel（性能要和 DeepInfer 可比）都在这一个 PR 里；顺序是先让整个模型在 4 张卡上按官方的算术跑出文本，再上融合 kernel，再做 EPLB。

### 10.1 DeepInfer 是怎么做的（`a679bb8`，读代码和它的 Q&A）

- **进程组**：每个 worker 先进一个 gloo 的默认组，再按 DP、EP、Engram 建 NCCL 子组（`worker/base.py`、`parallel_utils/parallel_state.py`）。DeepEP 和 DeepGEMM 拿的是这个 `ProcessGroup`。
- **MoE**：EP 组在一个 NVLink 域里时（EP1 也算），一律是 `deep_gemm.fp8_fp4_mega_moe` 加一块对称内存 `SymmBuffer`：dispatch、两次 GEMM、combine 是一个 kernel（`v4_modules/mlp.py`）。DeepEP 的 `EPBuffer.dispatch/combine` 只是跨出 NVLink 域（多机）时的路。
  - 每个 rank 把自己的 token、选中的专家和权重写进自己那块对称内存，kernel 把 token 推到持有专家的 rank 上去；每个 rank 这一步有多少 token 是 kernel 的参数，各 rank 可以不同，0 也行。
  - 所有 rank 必须在同一步里各调一次这个 kernel，kernel 里互相等，等 60 秒超时就是设备断言。
- **Hyper-Connections**：`deep_gemm.mega_mhc` 一次调用做完上一个子层的 post、这个子层的 pre（含 Sinkhorn）、RMSNorm 和 FP8 量化，量化结果可以直接写进 MoE 的对称内存（`v4_modules/hc.py`）。
- **EPLB**（`model_executor/eplb/`）：gate 里把逻辑专家映射到物理槽位，每张卡多留几个槽位放热点专家的副本；MoE 的 kernel 顺手数每个专家收到多少 token；每隔 N 步按最近一窗的统计贪心地重排，权重经对称内存在卡之间搬。
- **Engram**：`deep_ep.EngramBuffer`，表按行分在 Engram 组的各 rank 上，forward 一开始就按哈希把所有层要的行取回来。默认放主机内存、用 RDMA 读，也可以放显存。

### 10.2 做了的

**调度域**（`core.sched`，[engine/core/sched/README.md](../../engine/core/sched/README.md)「调度域」）。`sched.domains` 把 rank 按顺序分成几个域：
- 每个域有自己的行、自己的账本（`ledger.domains@1`）、自己的一份给 compose 策略的视图，跑自己的请求；
- 一步是给每个 rank 各发一份计划，没事做的域发空计划；
- 一个域拒了一步（`Resync`）不影响别的域这一步的结果。
- 默认一个域，行为和以前一样（原有的 79 个调度测试不变地通过）。

**通信组**（新单元 `worker.comm`，`comm.group@1`）。照 DeepInfer 的建法：默认组 gloo，`comm.device_backend = nccl` 时另建一个卡上的组。`comm.size = 1` 时什么都不建，所以所有模型族的 worker 都装着它。它给参照 kernel 两个 collective：`gather`（各 rank 行数不同的张量拼起来）和 `reduce`（求和）。

**专家和 Engram 表分在各 rank 上**（`comm.size > 1`）：
- 模型按 rank 声明和装载自己的那一份：每层专家的 `1/ranks`，Engram 表按行连续切的一段（最后一段补零）。权重存储只读自己要的专家和表的那几行（`weight_rows`）。
- 两个新 definition（`kernels/ds1017_ep.py`，参照和 `tilelang` 后端共用一份写法）：
  - `ds.ep_experts@1`：各 rank 把这一步的 token 拼到一起，每个 rank 用自己后端的专家 kernel 算自己持有的专家，结果求和，再由 token 所在的 rank 加起来。
  - `ds.engram_fetch@1`：同样的办法取表的行。
- **和单 rank 逐位相同**，靠三点：
  - 一个专家对一个 token 的那一项只取决于这个 token（底下的 kernel 是逐行独立的），所以在哪个 rank、和哪些别的 token 一起算都一样；
  - 每个 rank 把每个 token 的每一项单独送回（不是先求和）：一个 token 的一次选择只有一个 rank 有值，其余是 0，跨 rank 求和得到的就是那一项；
  - token 所在的 rank 按专家编号的顺序把它的各项加起来，和单 rank 的 `moe_experts` 的加法顺序相同。
- 没有请求的 rank 每一步也要参与每一层（`model.idle`，executor 收到空计划时调它）：别的 rank 的 token 可能选了它的专家、哈希到它的行。
- 这两个 definition 的参照和 `tilelang` 版本经主机或 NCCL 的 collective 交换，录不进 graph；`core.plan` 因此不录图，并在它那一行里写明是哪个 kernel。后端 `deepinfer` 的版本（`mega_moe`、`EngramBuffer`）属于后面的融合 kernel，在那之前点名 `deepinfer` 加多 rank 会在启动时报缺这个 definition。

**部署**：`agxinfer serve --gpus 0,1,2,3` 每张卡一个 worker，`--ranks N` 在一张卡或 CPU 上起 N 个。每个 worker 一个调度域；DS 的配方把它们设成一个通信组（碰头用 run 目录下的一个文件）。

**前端**：tokenizer 目录里的 `chat_template.jinja`（DS 的 checkpoint 是这样放的）、模板自己的参数（`frontend.chat_template_kwargs`，例如 `{"thinking_mode": "chat"}`）、纯文本提示词前面加 BOS（`frontend.add_bos`，DeepInfer 也是这样改 tokenizer 的）。

### 10.3 一处框架改动

`core.change` 的协调者原来是一个一个地启动进程，等前一个 check in（单元都加载完）再起下一个。通信组的 rank 在加载单元时要互相等（碰头；以后还有对称内存、带 collective 的 graph 录制），第一个 worker 永远等不到第二个，引擎起不来。

- 改成：同一个角色的进程一起启动，角色之间仍然一个一个来，重启在新建之前，和原来一样。每个角色只有一个进程时没有任何变化。
- 单元这一侧绕不过去：把碰头推迟到第一步可以让进程先 check in，但录 graph 是在单元加载时做的，带 collective 的 graph 必须所有 rank 同时录。
- 验证：框架测试和全量测试通过，formal 全流程（TLC 加轨迹回放）通过。

### 10.6 EPLB（2026-11-15）

照 DeepInfer 的 `model_executor/eplb/` 做，拆成两个 worker 单元：

- **策略** `policies.eplb`（`policy.rebalance@1`）：只做决定。从 DeepInfer 的 `eplb/policy.py` 搬来，两遍贪心：
  - 先把多出来的槽位一个一个分给"每个副本负载最大"的专家；
  - 再把所有副本按负载从大到小发给各 rank，每次放到"让各步里最忙的 rank 的负载之和最小"的那个 rank 上。
  - 本地拿随机负载对过 DeepInfer 的原实现（含真实大小：384 个专家、416 个槽位、每 rank 104 个），放置完全相同。
  - 它是一个独立的单元，换算法就是换这个单元，可以在跑着的引擎上 apply。
- **机制** `state.expert_placement`（`expert.placement@1`）：
  - 每层 `logical` 个专家放在 `physical` 个槽位里，每个 rank `local` 个；`eplb.extra_experts` 是多出来放副本的槽位数（向上取整到每个 rank 一样多）。初始布局和 DeepInfer 一样：先按 checkpoint 的顺序放一遍，多出来的槽位再从头放。
  - kernel 读的两样：`physical(layer, indices)` 给每个被选中的专家挑一个槽位（有副本的按 token 在这一步里的位置轮着用），`count(layer)` 让专家 kernel 把这个 rank 每个槽位收到的 token 数加进去。
  - 每个 forward 结束调一次 `step`：这一步的计数进一个窗口（最近 `eplb.window` 步）。每 `eplb.interval` 步（第一次提前到四分之一处）各 rank 把窗口按专家求和，交给策略算新的放置，然后逐层搬权重：rank 内部直接拷，跨 rank 的那些行用一次 `gather` 交换。每个 rank 从同样的映射算出同样的搬法。
  - `eplb.interval = 0` 且没有多余槽位时，或者只有一个 rank 时，它什么都不做。
- **模型这一侧**：权重按槽位声明（每 rank `physical / ranks` 个），装载时把专家写进这个 rank 上初始属于它的每个槽位；权重被重新装载以后放置回到初始布局。
- **不改变算出来的结果**：同一个专家在哪个槽位权重都一样，一个 token 的那一项在哪个 rank 上算都一样，token 所在的 rank 仍按专家编号的顺序加。所以开着 EPLB、权重在请求之间搬来搬去，文本和单 rank 逐字相同（`tests/scenarios/test_ds1017.py` 的 `balanced` 那一组：2 个 rank，每 4 步重排一次）。
- **整个模型上**（SM100，4 张卡，真权重，`tilelang`，同一个任务）：`eplb.interval = 16`、窗口 16 步、每层多 32 个槽位（416 个，每卡 104 个）。4 个提示词各 48 个 token 的一轮里重排了 15 次，最后一次动了 15474 个槽位，最忙的 rank 承担的 token 从平均值的 1.344 倍降到 1.050 倍（DeepInfer 自己在 EP4/DP4 上报的是 1.074）。文本和不开 EPLB 的那一遍逐字相同。每 16 步重排一次是为了测试压出来的频率，吞吐从 7.6 降到 6.9 tokens/s；DeepInfer 的默认是 decode 每一万步一次。
- 本地 4090 D（两个 worker 共用一张卡）：参照和 `tilelang` 各重排 42 次，文本和不开、和单 rank 都相同。
- 现在接上的是参照和 `tilelang` 后端的专家 kernel。DeepInfer 的 gate（`bf16_mega_gate`）和 `mega_moe` 自己吃这两张映射和计数（`to_physical_map`、`logical_count`、`cumulative_local_expert_recv_stats`），接它们的时候直接把这里的张量交过去；权重在卡之间搬，DeepInfer 用对称内存直接读对端，这里先用 collective，够不够快到时候量。

### 10.7 融合 kernel（2026-11-15）

用户 2026-11-15 定：融合大 kernel 要上，目标是性能和 DeepInfer 可比。做法是把层里两处"一串小 kernel"各收成一个组合 definition，参照和 `tilelang` 后端仍是原来那些 kernel 按原来的顺序组合，`deepinfer` 后端换成 DeepGEMM 的融合 kernel。

**两个组合 definition**（`kernels/ds1017_compose.py`）：

| definition | 内容 | 参照、`tilelang` | `deepinfer`（`kernels/deepinfer/mega.py`） |
|---|---|---|---|
| `ds.hc_step@1` | 两个子层之间：上一个子层的输出写回残差流、算下一组系数、这个子层的输入（混合加 norm） | `hc_post`、`hc_mixes`、`hc_pre`、`rms_norm` | `deep_gemm.mega_mhc` 一次做完；子层是 MoE 时，把输入的 FP8 形式直接写进 MoE 的缓冲区 |
| `ds.moe@1` | 一层的 MoE：gate、路由专家（多 rank 时到持有专家的 rank 上算）、共享专家 | `moe_gate`、`moe_experts` 或 `ep_experts`、`shared_expert` | `bf16_mega_gate` 加 `fp8_fp4_mega_moe`（带共享专家），单 rank 也走这条 |

- **模型的循环按 DeepInfer 的顺序重排了**（`HCLayerMixin._hc_fused_post_pre` 的"惰性 post"）：一个子层的输出先不写回残差流，由下一个子层之前的 `hc_step` 写回。对参照和 `tilelang` 只是把同样的 kernel 换了个分组，调用和顺序都没变，所以仍和官方参照实现逐位相同（本地 `tests/gpu/test_ds1017.py` 7 个全过；SM100 上真实形状和真权重 8 层都是 16 步逐位相同，任务 `20261115T134749Z-9f886b7d`）。
- Engram 层之前和模型最后要用到残差流本身，那两处显式 `hc_post`；第一个子层没有要写回的东西，`deepinfer` 在那里走不融合的 kernel（DeepInfer 也是）。
- **MoE 的缓冲区**是 `deep_gemm.SymmBuffer`：多 rank 时是经 NVLink 的对称内存，单 rank 时是普通显存。它是进程在一个集体对象里的那一份：第一次调用时建（各 rank 的第一次调用在同一步里），由 `kernels.deepinfer` 的单元实例持有、卸载时销毁。
  - 各 rank 每一步各调一次 `mega_moe`，带自己这一步的 token 数，可以不同，0 也行（空转的 rank）。
- **权重的行顺序跟着读它的 kernel 走**：融合 MoE kernel 要专家的 `w1`、`w3` 每 8 行交错，scale 按它装载的顺序排。`formats.expert_layout`、`shared_layout` 就地做这个行置换，也能就地还原（和 DeepGEMM 自己的 `transform_weights_for_mega_moe` 对过，逐位相同）；模型在权重存储里放一个标记，后端换了就置换回去，不用重读权重。
- gate 的权重另存一份 bf16（`ffn.gate.bf16`，checkpoint 里就是 bf16）：融合 gate 的乘法是 bf16 的，参照仍用 fp32 的那份。
- 模型的形状不适合融合 kernel 时（残差流不是 4 份、宽度不是 1024 的倍数等），`deepinfer` 后端退回用它不融合的 kernel 做同样的组合（`deepinfer.unfused.*`）。
- **录 graph**：`mega_mhc` 和 `bf16_mega_gate` 各有一小块按 stream 分的缓冲，第一次在某个 stream 上调用时建，不能在录制中建；引擎的录制器本来就先在录制用的 stream 上预热一步。多 rank 时 Engram 的行在 forward 之前取（`Backend.fetch`，在 graph 之外），所以录下来的一步里的 collective 只有 `mega_moe`。
- torch 的对称内存默认认为设备号相同的 rank 在同一张卡上；我们和 DeepInfer 一样每个 rank 只看得见自己的卡（都是 0 号），要设 `TORCH_SYMM_MEM_ALLOW_OVERLAPPING_DEVICES=1`（`worker.comm` 加入通信组时设）。

**SM100 上的结果**

| 检查 | 结果 |
|---|---|

### 10.8 Attention 融合、`EngramBuffer` 与 4 卡在线热改（2026-11-16）

承接 10.7 的交接项，在 `dev/ds1017-ep` 上补齐了另外半边融合算子、分布式 `EngramBuffer`、prefill 预热以及多卡热改验证（详细过程与耗时见 [../rsi/2026-11-16-ds1017-multi-gpu-hot-apply-and-fusion.md](../rsi/2026-11-16-ds1017-multi-gpu-hot-apply-and-fusion.md)）：

- **新增四个组合 definition**（`kernels/ds1017_compose.py`）：
  - `ds.attn_qkv@1`、`ds.cache_attn_out@1`、`ds.sparse_attn_out@1`：`deepinfer` 后端由 `mega_mhc` 直接给出 attention 输入的 FP8 形式，合并 `wq_a + wkv` 投影，调 FlashMLA 的 `fused_norm_rope_attn_rope_cast` 并融合输出投影；参照和 `tilelang` 保持原算子组合。

- **4×SM100 在线热改与 EPLB + `deepinfer` + CUDA Graph 实测**：

  - 忙时默认拒绝（**2.37 秒** `aborted`）、`--wait-empty`（排水期新请求返 `503`、在途返 `200` 后提交，**9.53 秒**）、`--force`（**6.50 秒**）全部验证通过；
