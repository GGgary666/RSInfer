## 0. 一句话

v0 是一个**架构正确、所有变更路径都能端到端走通的真实推理引擎**：
- 在单台 SM100 机器上跑 Qwen3.8-27B（TP1，以及一种多 rank 的 TP 配置）。
- 每个模块都是一个**单元**，单元是管理和重载的最小单位；进程只是装单元的容器。改了逻辑单元，只重载它和依赖它的单元，进程不重启。
- 框架本体几乎不带领域概念：没有内建的“调度器”“KV cache”“TP”，这些全是单元。框架只负责把单元拼起来、换下来。
- 开发时，agent 在常驻实例上用 `apply` 自由修改；评测时，向评测服务提交 patch，冷启动评测。
- **不追求性能**：v0 可以很慢，但架构必须正确，而且要足够有表达力，能按思想实验的路线演进成 v0.1、v0.2。

## 3. 设计立场

### 3.1 框架提供机制，不规定 RSI

使用者自带优化目标、agent 和 LLM、搜索方法、评测套件、门禁。框架保证：
- 任何改动都能安全地应用和回滚，并且返回诚实的结果：要么成功应用，附上实际执行的动作计划；要么 `failed`，附上诊断信息，并且已经回滚。
- 任何结果都能追溯到确切的系统身份。
- 评测在候选的边界之外，在冷启动的独立实例上进行。
- 改动可以叠加：被接受的身份可以成为新的基线，可以分支，也可以合并。

### 3.2 引擎本体就是产品

- 引擎（前端、控制面、调度宿主、worker）单独就能部署，地位和 vLLM、SGLang 相同。
- RSI 平面（评测服务、谱系、发布导出）是引擎源码树之外的插件包 `rsi/`，不计入引擎身份，patch 改不到它。依赖只有一个方向：RSI 平面 → 引擎。
- CI 检查：不安装 `rsi/` 时，引擎照样能构建、服务、`apply`。

### 3.3 开发和评测分开

- **常驻实例**：agent 启动后一直运行，接受 `apply`。被反复改过，结果只供参考。
- **评测服务**：只接受 patch，自己持有起点快照，每次都冷启动起点和候选。“这个改动是不是真的更好”只能由它回答。
- `apply` 和评测共用同一种 change-set 格式：`apply` 打到正在运行的实例上，评测服务打到干净的起点快照上。

### 3.4 不追求性能

判断一个特性要不要进 v0，看它会不会对状态、plan 或变更机制提出新的要求，而不看它能不能让引擎更快：
- 对架构有新要求的特性：做一个最简单的正确版本，证明架构装得下。v0 里有：前缀复用（按块哈希匹配）、CUDA graph（decode 默认开，分桶取 2 的幂）、固定长度投机解码、权重原地替换（refit）、KV 池扩容（grow，启动时预留虚拟地址）、融合组（只有机制，默认不融合）。
- 只影响快慢的优化：v0 一律不做，留给使用者的 RSI。比如异步调度、调度策略调优、kernel 融合、graph 分桶调优、通信重叠、torch.compile。
- EP 和 EPLB 对架构有要求，但 Qwen3.8 用不到，所以放在 v0.1。v0 要保证的是：按思想实验一的路线加上它们时，不需要改框架本体。
- 如果 v0 慢到快速测试或评测跑不完，只针对那一个瓶颈做最小的改动。

## 5. 架构

modules.html 是这一节的完整版本（全景图、单元清单、场景演示）。这里只写要点。

### 5.1 单元模型

- **单元**声明自己要用哪些服务、提供什么服务、读哪些配置、属于哪一类、支持哪些动作。单元通过服务名找对方，不 import 别的单元的对象。
- **所有注册都可撤销**：注册 kernel、绑定策略、起线程、开 CUDA stream、`torch.library` 注册……每一项都返回撤销函数。卸载单元，就是把撤销函数倒着执行一遍。
- **依赖自动传播**：某个服务的提供者被换掉，依赖它的单元自动卸载，等新提供者就绪再装上。
- **代码重载**：按 import 图找出受影响的单元，清掉模块缓存、重新 import、卸旧装新；中途出错就回滚。
- **配置原地生效**：单元可以注册钩子，原地接受新配置；否则只重载这一个单元。
- **被重载的单元不保留内存状态**，要保住的东西放在状态单元里。

比 Cordis 多做五件事：只在 epoch 边界换；同一组的所有 rank 用两阶段提交一起换；派生产物（CUDA graph 等）登记依赖，上游变了通知重建；卸载顺序按依赖反方向，先卸用显存的一方；跨机器（P7）。

### 5.2 三类模块和动作阶梯

- **逻辑单元**：代码、策略、模型、kernel、调度逻辑、plan 编译。重载便宜。agent 绝大多数改动落在这里。
- **状态单元**：显存、权重、KV、各种 state、通信组、请求表、账本。重载会丢掉持有的状态，v0 默认先排空再重建。它们管的内容通过状态动作改。
- **框架本体**：七个组件，改了重启引擎，极少改。

动作从便宜到贵：
0. 不动；
1. 原地接受新配置；
2. 重载单元（依赖它的单元跟着重载）；
3. 重建派生产物（重录 graph）；
4. 状态动作（refit、grow、migrate、invalidate）；
5. 重启进程（native 扩展、并行拓扑变化、NVSHMEM 首次初始化、进程崩溃）；
6. 重启引擎（框架本体变了，或者平台升级）。

只有会影响在途请求的动作才排空，而且只排空受影响的那部分请求。**改配置的值从来不重启引擎**：每步现读的键下一个 epoch 生效；录进 graph 的键后台重录；决定 KV 池大小的键走 grow；决定拓扑的键只重建 rank 进程。

### 5.3 进程拓扑

| 进程 | 数量 | 装的东西 |
|---|---|---|
| 前端 | 1 | OpenAI 接口、分词、反分词三个单元 |
| 控制面 | 1 | 控制接口、变更事务（本体）、系统身份、清单与静态检查、影响分析、进程管家（本体） |
| 调度宿主 | 1 | 调度逻辑、各个策略、请求表（状态）、账本（状态） |
| worker | 每 rank 1 个 | 逻辑单元：每步执行循环、plan 编译与 graph、执行后端、模型、层、MoE 流水线、通信逻辑、kernel 目录、kernel 实现。状态单元：显存持有者、权重存储、通信组、状态种类 |
| 节点代理 | 每台机器 1 个 | 本体：替进程管家拉起本机进程、物化代码快照、提供本机共享内存通道、上报健康和平台信息 |
| 评测服务、谱系服务 | 按需 | RSI 平面，只通过公开接口和引擎交互 |

每个进程里都有：单元运行时、配置与运行环境、进程间传输、平台（本体），以及自省（单元）。

进程之间只走三种通道：ZMQ（请求和控制）、共享内存或 TCP / RDMA（每步的记录，按两端是否同机自动选）、RPC（变更事务）。显存不跨进程共享。

### 5.5 边和绑定方式

边有六种：每步数据流、接口调用、状态共享、派生、变更控制、声明 / 注册。

派生边（以及“读配置”的边）带一个绑定方式，决定改了以后要不要重建：
- **实时**：每次执行都重新读，改了下一步就生效。
- **按地址**：graph 记住了显存地址。同地址、同 shape 和 dtype 只改内容，不用重建；换地址或改 shape / dtype 要重录。
- **按值**：录的那一刻的值被写死（选中的 kernel、标量参数、代码分支、分桶、DeepEP 模式），任何改动都要重录。

动作 = 改动的种类 × 边的绑定方式。依赖由 plan 单元在录 graph 时自动记录：查过的 kernel、读过的配置和运行时标志、记住的显存地址、执行过的代码；replay 前检查有没有变。清单里的声明只用来交叉校验。

### 5.6 七条原则

- **P1 用数据描述**：并行拓扑（mesh，含物理布局）、进程拓扑、张量的格式和放置、每层的状态声明都是数据，由单元解释。
- **P2 开放记录**：StepPlan、决策快照、StepResult 由各单元各自贡献分段。
- **P3 按 rank 索引**：TP 只是“每个 rank 都一样”的特例；账本按调度域分。
- **P4 能力声明**：单元声明支持哪些动作、能否录进 graph、能否跨机、需要什么平台能力、会不会改变 KV 数值。框架按声明推导动作。
- **P5 联合协议**：准入、前缀命中长度、分桶对齐，都是“各自给约束 → 机制合并”。
- **P6 变更来源统一**：agent、配置、单元自己（EPLB）、运维发起的改动都是 change-set。
- **P7 位置透明**：拉起进程走节点代理；通道按位置选后端；代码从本机按身份物化的快照目录加载；地址和路径来自拓扑数据；事务参与者按“机器 + 进程”寻址。

P1–P6 约束单元之间的接口；P7 约束框架本体自己，v0 不做对，以后补就要改本体。CI 在一台机器上起两个节点代理模拟两台主机，用假执行器验证 P7。

### 5.7 变更流程

1. 生成 change-set：工作区相对当前身份的差异，得到候选身份；内容按 hash 推到每台机器的节点代理，物化成本机快照。
2. 静态检查：清单、import 图、让重载可靠的规矩。不通过就返回 `failed`，当前版本继续服务。
3. 推导动作计划（`core.deps`）。带 `--dry-run` 时到这里就返回。
4. 准备：能在后台做的先做（装新单元、在第二套 buffer 里重录 graph）。这也是两阶段提交的 prepare，任一参与者失败就整体撤回。
5. 按需排空受影响的请求。
6. 在 epoch 边界让相关进程停下，执行推迟的动作，提交。
7. 恢复服务；返回新旧身份、实际执行的动作计划、各阶段耗时、诊断信息，并写入事件日志。

启动也当作一次变更（从空系统到某个身份）。

### 5.8 版本切换语义

- 同一时刻只有一个版本在执行。原因：新旧版本可能连并行方式都不同。
- 按需排空：没有影响在途请求的动作时，下一个 epoch 直接生效；有的话，只排空受影响的请求，新到达的请求排队，排满了返回 503 加 `Retry-After`。
- 每个响应的 HTTP 头 `x-engine-identity` 写请求开始时的身份；跨过切换的请求，在最后一个事件里列出经历过的全部身份。

### 5.9 change-set 和系统身份

- change-set：起点身份；文件 → 新内容的 hash（删除记为 null），另附 unified diff 用于审查；配置键 → 新值；依赖锁的变化；大产物按内容 hash 引用；提交者、意图、证据链接。
- 应用是确定的：候选身份 = f(起点身份, change-set)。
- 身份覆盖：每个单元的源码和清单、声明过的配置键的生效值、依赖锁、模型规格和权重清单、kernel 绑定、状态布局版本、拓扑数据、每台机器的平台信息。机器之间平台信息不一致就拒绝启动。

### 5.10 状态

- **状态声明**：每层声明自己存的部分——寿命（整个请求 / 滑动窗口 / 每请求一个 slot）× 每项对应几个 token × 形状 × 放在哪（显存 / host）× 自有还是借用别的层的 × 快照对齐 × 分区。借鉴 sglang `mem_cache/kv/decl.py`。
- **一种状态 = worker 里的一个存储单元 + 账本里的一个记账插件**，两者用同一份声明。
- 存储单元实现 allocate / free / snapshot / invalidate（必须有），以及可选的 migrate / refit / grow，并声明自己支持哪些。
- 账本：每个调度域一本；联合准入（几种状态必须一起分到）；联合前缀匹配；不变量检查（空闲 + 占用 = 总数、没有重复分配、每个请求最终都会释放）。
- 权重：逻辑张量 = 格式（插件）+ 放置（数据）；按逻辑名寻址，带版本；支持 refit；路径按机器解析。
- Qwen3.8 的状态：16 层 full attention 的 paged KV；48 层 GDN 每请求的 recurrent state（FP32）和 conv state，做前缀复用时在块边界打快照。

### 5.11 plan 与 kernel 目录

- kernel 目录：definition（语义、PyTorch 参照实现、容差、是否 batch-invariant）和 solution（库、shape 约束、能否录进 graph、能否跨机、是否需要进程级初始化）。按 definition + shape 选 solution，编 plan 时定死；选不到就退回参照实现并标注。schema 和 flashinfer-bench 对齐。
- plan：每个（阶段, 分桶）一个，从实际跟踪模型前向得到，不假设每层同构。只有 plan 单元能录 CUDA graph；双缓冲，新 graph 在后台录，epoch 边界切换。
- 任何单元都可以向 `core.deps` 登记派生产物（plan、graph、缓存的映射表、实测曲线）及其依赖。

### 5.12 调度

- 机制（`core.sched`）：请求状态机、联合准入、batch 合法性校验、抢占执行、多 rank 同步推进（空 rank 跑空 batch）、生成按 rank 索引的 StepPlan、标出 epoch 边界。
- 决策点（`policies.*`）：准入与 DP 路由、排序、chunk 大小、抢占对象、投机验证长度、graph 分桶、缓存淘汰、EPLB（v0.1）。输入是只读快照，输出是决定，由机制校验。默认实现都最简单：先来先服务、固定 chunk、抢占最新到达的、固定验证长度、LRU。
- 同步调度，不做异步调度；快照时效作为快照上的一个声明属性，留给以后。
- 请求表只追加日志，进程崩溃后靠它恢复。

### 5.13 其他单元

- CI 假执行器：按 shape 分配 buffer、按配置 sleep、在指定位置注入故障；不许加模型语义。
- 前端：`chat/completions`、`completions`、流式输出；Qwen3.8 用 HF tokenizer 加 chat template。
- 控制 API：`engine serve --source <工作区或 commit> --model qwen38`；`apply [--source] [--dry-run]`、`status`、`introspect`、`logs`。常驻实例由 agent 自己管。
- 评测服务：`eval submit --base <起点身份> --patch <change-set> --suite <套件@版本>`。校验（起点存在、能确定地应用、受保护路径、静态检查）→ 物化 → 冷启动 → 套件（Workload + Gates + Scorers + Protocol）→ 结果按（起点, patch, 套件版本）写入谱系。另有本地自检 `engine selfcheck`。
- 谱系：内容快照放在 bare git 仓库，身份、边、事件、评测结果放在 sqlite（本机路径），大产物放在内容寻址的 blob 存储；支持分支、promote、rebase、merge；`release export` 导出发布产物，部署时不需要 RSI 平面。

## 6. 模型规格

### 6.1 Qwen3.8-27B（v0）

- 结构：64 层，其中 48 层 GatedDeltaNet、16 层 full attention；BF16 权重约 55.6 GB，TP1 就能放进单张 SM100。各项尺寸以 checkpoint 的 config 为准，M0 核对。
- 实现来源：语义以 HF modeling 为参照，工程实现参考 vLLM 和 sglang；kernel 来自 flash-linear-attention（GDN）、FlashInfer 或 FlashAttention（attention），以及 kernel gateway 已有的三道题（gated RMSNorm、causal conv decode、recurrent GDN）。
- 投机解码：checkpoint 带 MTP 层就用 MTP，不带就用 n-gram 草稿（M0 核对）。
- 正确性参照：HF 参照实现，以及同一硬件上 vLLM 或 sglang 的输出。

### 6.2 DS 1017（v0.1；M0 纸面包络测试要用）

v0 不实现 DS 1017，但 M0 必须用它做纸面包络测试，确认每种算子和状态都能用 v0 的接口表达。下面的数字来自 HF 上的 `config.json`：
- 主干：40 层，hidden 5120，64 个 head，1 个 KV head，head_dim 512（其中 RoPE 64），q_lora 1280，o_lora 1024，o_groups 8；词表 129,280；最长上下文 1,048,576（YaRN，factor 16）。
- attention：`compress_ratios` 共 43 项（推测是 40 层主干加 3 个 nextn 层），每项取值 0、1、2；`sliding_window` 128；indexer 32 个 head，head_dim 128，top-k 512；candidate 选块：源层 20，选 2048 个块，块大小 8。
- 跨层共享：`kv_source_layer_ids = [2, 8, 14, 20]`，`index_source_layer_ids = [2, 8, 14, 20, 24, 28, 32, 36]`。
- MoE：384 个路由专家加 1 个共享专家，每个 token 激活 6 个；intermediate 2304；打分函数 sqrtsoftplus，`noaux_tc`。
- mHC：`hc_mult` 4，Sinkhorn 迭代 20 次。Engram：在第 1 层和第 14 层，两张表各约 3.84 亿行，n-gram 最长 4，8 个 head，head_dim 256。
- 投机：3 个 nextn 层。量化：FP8 块量化（32×32，ue8m0 scale），专家是 FP4；整个 checkpoint 476 GB。
- 状态：压缩 block KV（FP4，128 token 一页，跨层借用）、indexer K（MXFP4，跨层借用）、每序列 state slot（SWA 环形缓冲和压缩累加器，分可持久 / 可丢弃两区，128 token 边界快照）、nextn KV、Engram 大表（host 内存）。
- 环境前提：DeepInfer 要求 NVCC 13.1 以上、`torch 2.13+cu132`；第三方报告说单机也需要 RDMA 设备。
- 最大的不确定性：状态声明够不够宽。sglang 支持 DS V4 时另写了专用显存池（`mem_cache/deepseek_v4_memory_pool.py`）。

## 7. 验收路径

“环境”一列：CI = 假执行器；快速 = 单张 SM100 上的参照实现加小尺寸配置；全模型 = 真实权重和真实 kernel。

| # | 路径 | 环境 | 验收要点 |
|---|---|---|---|
| P1 | 从一个身份冷启动并开始服务 | CI、快速、全模型 | 前端返回带身份的响应 |
| P2 | 替换一个策略单元 | CI、快速 | 只重载这一个单元，不排空；下一个 epoch 生效 |
| P3 | 换 graph 里的 kernel | 快速、全模型 | 后台重录受影响的 graph 后提交；人为跳过重录时，运行时守卫必须拦下 |
| P4 | 改调度机制的代码 | CI、快速 | 只重载调度逻辑单元；请求表和账本不动，在途请求不丢，不重启进程 |
| P5 | 改模型、层或 worker 主循环的代码 | 全模型 | 单元级重载，进程不重启、不重新加载权重；需要时重录 graph 并能正确 replay；记录实际耗时 |
| P6 | 状态布局变化 | 快速 | 有迁移函数时迁移；没有时按声明失效或重建 |
| P7 | 改状态单元、native 扩展、框架本体 | CI、全模型 | 状态单元：排空并重建；native 扩展：只重启 rank 进程，调度宿主和前端不停，排队的请求不丢；本体：重启引擎，谱系和事件日志不丢 |
| P8 | `failed` | CI | 静态检查不通过、prepare 失败、某个 rank 故障，都撤回，旧版本继续服务，返回诊断 |
| P9 | 跨 rank 事务 | CI、全模型（Qwen 的多 rank 配置） | 向第 k 个 rank 注入 prepare 故障，所有 rank 都撤回 |
| P10 | 依赖传播 | CI | 提供者单元被重载，依赖它的单元自动重载；卸载按依赖反方向，先卸用显存的一方 |
| P11 | patch 评测 | 快速、全模型 | 校验、物化、冷启动、成对测量，结果写入谱系并附 diff |
| P12 | 起点漂移 | CI | 旧起点上通过的 patch 不能直接 promote 到已前进的基线；rebase 并重新评测后才可以 |
| P13 | 受保护路径 | CI | 碰了受保护路径的 patch 在校验阶段被拒绝，不占 GPU |
| P14 | 本地自检和评测服务一致 | 快速 | 门禁结果相同，性能差异在噪声范围内 |
| P15 | 谱系 | CI | 并行分支、promote、merge；merge 得到的身份不重新评测就不能 promote |
| P16 | 发布与部署 | 全模型 | 导出发布产物；没有 RSI 平面也能部署；部署后照样可以 `apply` |
| P17 | 拆除检查 | CI、快速 | 不安装 `rsi/` 时，构建、服务、`apply` 都正常 |
| P18 | 同一模型的新权重 | 快速、全模型 | 原地 refit：plan、graph 不变；KV 和前缀缓存失效；依赖权重数值的派生量重算；排空超时很短时，剩余请求以“因版本切换中止”结束 |
| P19 | 扩大 KV 池 | 快速、全模型 | 不排空、不重载任何单元；graph 仍然有效；新容量立即可用 |
| P20 | 改并行配置（TP1 和多 rank 配置互换） | 全模型 | 只重建 rank 进程；控制面、前端、调度宿主不停；排队的请求不丢 |
| P21 | `--dry-run` 和实际执行一致 | CI、快速 | 每种改动的动作计划和实际执行的动作完全一致 |
| P22 | 按需排空 | CI、快速 | 不影响在途请求的改动不触发排空；跨过切换的请求列出经历过的全部身份 |
| P23 | 改配置的值 | CI、快速 | 实时读的键下一个 epoch 生效；录进 graph 的键后台重录；都不重启引擎 |
| P24 | 位置透明 | CI | 一台机器上两个节点代理模拟两台主机，强制走 TCP、各用各的快照目录，P1、P2、P8、P9、P20 照样通过 |

## 11. 风险

| 风险 | 表现 | 缓解 |
|---|---|---|
| Python 热重载不可靠 | 旧对象引用残留、全局注册撤不掉、C 扩展卸不掉 | 静态检查守规矩（不 import 别的单元的对象、注册可撤销、没有模块级可变全局）；native 扩展声明出来，改了走重启进程；重载前后的注册表对比 |
| 状态声明不够宽 | v0.1 加 DS 状态时要改接口 | M0 拿 DS 1017 做纸面包络测试 |
| P7 没做对 | v0.2 要改框架本体 | CI 里两个假主机的 P24 |
| 卸载顺序出错 | graph 读到已释放的显存，静默出错 | 卸载按依赖反方向；植入缺陷测试 |
| 动作推导漏掉受影响的节点 | 该重建的没有重建 | 推不出来就升级；dry-run 一致性；运行时守卫 |
| 基线偏弱 | RSI 的改进不一定能迁移到成熟引擎 | 需要强基线的使用者从“已优化”的谱系分支出发（待确认） |
| 大尺寸下没有 batch-invariant kernel | 全模型上做不到精确门禁 | 精确门禁放在快速测试层；全模型用容差门禁加生成式质量评测 |
| 假执行器膨胀 | 慢慢变回模拟器 | 硬规则：需要正确性的测试一律放到快速测试层 |
| 评测成本翻倍 | 成对测量要同时跑起点和候选 | 正确性参照按（身份, 套件版本）缓存；套件可以复用缓存的基线 |
| 清单负担太重 | agent 频繁拿到 `failed` | 诊断要可操作；新单元用模板生成清单；给 agent 写使用文档 |
| 后台准备新版本占显存 | 新旧 plan、graph 同时占显存 | 显存不够时改为排空以后再准备 |
| 没有任何隔离和鉴权 | 任何能访问控制端口的人都能 `apply` | 文档写明；v0 有意不做 |
| 环境变量不受限制 | 通过环境变量改变行为的改动看不出来 | 评测服务用固定环境变量冷启动并记录 |
